Dado, informação, conhecimento e inteligência

Esse é um dos assuntos mais importantes porque a banca pode apresentar uma situação prática e perguntar em qual estágio determinado elemento se encontra. Podemos pensar na seguinte evolução: DADO.

O que é DADO?

Dado é uma representação de um fato, evento ou observação, normalmente sem contexto suficiente para produzir uma conclusão por si só. Exemplo: 1250. Esse número isoladamente é um dado. Não sabemos: 1.250 o quê? Em qual período? Onde? Comparado com qual referência? É bom ou ruim?

Exemplo empresarial

Imagine uma empresa registrando: Janeiro 1.200; Fevereiro 1.350; Março 1.480. Esses valores são dados. Ainda não sabemos necessariamente o que significam.

O que é Informação?

A informação surge quando os dados são organizados e contextualizados, adquirindo significado. Por exemplo: "A empresa transportou 1.480 cargas em março." Agora sabemos o que representa o número, qual período e qual unidade de medida.

DADO 1.480 + CONTEXTO cargas transportadas em março = INFORMAÇÃO

Regra para prova: dado possui significado limitado isoladamente; informação é dado contextualizado e interpretado.

Conhecimento

O conhecimento surge quando informações são relacionadas à experiência, regras, contexto e compreensão sobre determinado fenômeno. Exemplo: a empresa observa "O Terminal C apresentou 18% de atrasos" — isso é informação. Após análise histórica, a equipe percebe: "Sempre que o volume de cargas ultrapassa determinado nível, os atrasos aumentam significativamente no Terminal C." Agora existe conhecimento sobre o comportamento operacional.

Inteligência

A inteligência está relacionada à capacidade de utilizar dados, informações e conhecimento para orientar ações e decisões.

Dados → Informação → Conhecimento → Inteligência

Exemplo completo

  • Dado: 18%
  • Informação: O Terminal C apresentou 18% de atrasos em agosto.
  • Conhecimento: Historicamente, os atrasos aumentam quando o volume ultrapassa determinado limite.
  • Inteligência: A capacidade operacional deve ser ampliada antes dos períodos de alta demanda.
  • Decisão: Alocar recursos adicionais para o Terminal C.

Pegadinha

A banca pode afirmar: "Um dashboard contendo números é automaticamente informação." Não necessariamente. Os dados precisam estar contextualizados e possuir significado para o usuário.

BI não é apenas uma ferramenta

BI não significa simplesmente "utilizar Power BI". Uma ferramenta pode fazer parte de uma solução de BI, mas BI envolve também processos, dados e pessoas.

Exemplo de BI

Uma empresa possui: ERP, banco de vendas, sistema logístico, planilhas e CRM. O ambiente de BI pode integrar essas fontes. Depois: Dados → ETL/ELT → Data Warehouse → Modelo analítico → Dashboard → Gestor. O gestor consegue responder perguntas como: Qual região vende mais? Qual produto possui maior margem? Onde existem atrasos?

Características de BI

Integração de dados; análise histórica; acompanhamento de indicadores; identificação de tendências; descoberta de padrões; suporte à decisão; geração de relatórios; visualização de informações.

BI tradicional × análise operacional

Sistema operacional: "Qual é o status da carga 123?" — processamento operacional. BI: "Qual é a evolução dos atrasos por terminal nos últimos 24 meses?" — análise.

BI descritivo

Responde: O que aconteceu? Exemplo: "As vendas caíram 12%."

BI diagnóstico

Responde: Por que aconteceu? Exemplo: "A queda ocorreu principalmente na região Sudeste."

Análise preditiva

Responde: O que provavelmente acontecerá? Exemplo: "Mantido o comportamento atual, a demanda deverá crescer 15%."

Análise prescritiva

Responde: O que devemos fazer? Exemplo: "Recomenda-se aumentar a capacidade de atendimento."

Para memorizar: Descritiva (o que aconteceu); Diagnóstica (por que aconteceu); Preditiva (o que provavelmente acontecerá); Prescritiva (o que devemos fazer).

Mapeamento de fontes de dados

O que é uma fonte de dados?

É o local ou sistema de onde os dados são obtidos. Exemplos: banco de dados; ERP; CRM; arquivos CSV; planilhas; APIs; sistemas legados; sensores; aplicações web; arquivos XML; logs.

Por que mapear fontes?

Antes de construir uma solução de BI é necessário conhecer de onde vêm os dados. Imagine um indicador: "Percentual de entregas no prazo." Pode ser necessário obter: sistema de pedidos + sistema de transporte + sistema de entrega + calendário → indicador.

O que deve ser identificado?

Origem; proprietário; formato; estrutura; frequência de atualização; qualidade; volume; histórico; regras de negócio; segurança; relacionamento com outras fontes.

OLAP

O que significa OLAP?

OLAP — Online Analytical Processing — é uma abordagem voltada à análise multidimensional de dados. OLTP → operações transacionais; OLAP → análise.

OLTP x OLAP

OLTPOLAP
OperaçõesAnálise
TransaçõesConsultas analíticas
Inserções/alterações frequentesLeitura intensiva
Dados operacionaisDados históricos/analíticos
Ex.: vendaEx.: análise das vendas

Cubo OLAP

Dimensões: tempo; produto; região. Medida: faturamento.

Operações OLAP

Roll-up; Drill-down; Slice; Dice; Pivot.

Roll-up

Agregação dos dados para um nível mais alto de granularidade. Dia → Mês → Trimestre → Ano. Cidade → Estado → Região. Exemplo: 1º trimestre = 100 + 150 + 200 = 450.

Drill-down

Movimento contrário: sai de uma visão agregada para uma visão mais detalhada. Ano → Trimestre → Mês → Dia.

Para memorizar: Roll-up = sobe/agrega. Drill-down = desce/detalha.

Slice

Seleção de uma dimensão específica. Exemplo: Região = Sudeste.

Dice

Seleção de um subconjunto envolvendo múltiplas dimensões. Exemplo: Região = Sudeste; Produto = A e B; Ano = 2026.

Pivot

Alteração da perspectiva de visualização. Antes: Produto × Região. Depois: Região × Produto.

Data Warehouse

O que é Data Warehouse?

Repositório de dados orientado à análise, normalmente integrado e histórico, utilizado para apoiar decisões. Características: orientado por assunto; integrado; variante no tempo; não volátil.

Variante no tempo

Mantém histórico (Vendas 2024, 2025, 2026), permitindo comparar períodos.

Não volátil

Dados destinados à análise e não à alteração constante. A carga acontece e os dados ficam disponíveis para consulta.

Modelagem dimensional

O que é modelagem dimensional?

Técnica de modelagem voltada à análise de dados. Trabalha com fatos e dimensões.

Tabela fato

Contém eventos mensuráveis. Exemplo: FATO_VENDAS com data_id, produto_id, cliente_id, regiao_id, quantidade, valor.

Dimensões

Fornecem contexto. Exemplo: DIM_PRODUTO (produto_id, produto, categoria, marca); DIM_TEMPO (data_id, dia, mês, trimestre, ano).

Esquema estrela

Tabela fato no centro; dimensões ao redor (DIM_PRODUTO, DIM_CLIENTE, DIM_TEMPO, DIM_REGIAO).

Estrela x floco de neve

Estrela: dimensões desnormalizadas. Floco de neve: dimensões normalizadas em várias tabelas.

Granularidade

Nível de detalhe armazenado na tabela fato. Granularidade diária (venda por produto por dia); granularidade por transação (cada venda individual). Influencia armazenamento, consultas, desempenho e possibilidades de análise.

Otimização multidimensional

Técnicas

Agregações; índices; particionamento; escolha adequada da granularidade; otimização de consultas; pré-cálculo; armazenamento adequado; compressão; atualização incremental.

Relatórios

Operacional: atividades do dia a dia. Gerencial: acompanhamento do desempenho. Analítico: exploração mais aprofundada.

Dashboards interativos

Dashboard é uma interface visual que apresenta informações relevantes para monitoramento e análise. Pode permitir filtros; seleção de períodos; drill-down; cruzamento de dimensões; detalhamento; navegação entre páginas.

KPI

KPI — Key Performance Indicator — é um indicador-chave utilizado para acompanhar desempenho em relação a objetivos. Exemplo: percentual de entregas no prazo. Um KPI deve possuir relevância para um objetivo.

Manipulação de dados em planilhas

Planilhas podem ser utilizadas para: análise exploratória; tratamento; consolidação; cálculos; criação de tabelas dinâmicas; gráficos; preparação de dados.

Operações comuns: ordenação; filtros; fórmulas (=SOMA(B2:B100)); funções condicionais (=SE(B2>1000;"Alto";"Baixo")); PROCV/PROCX; tabela dinâmica; limpeza de dados.

Problemas comuns: dados duplicados; dados ausentes; formatos inconsistentes; valores inválidos.

Qualidade dos dados

Uma análise sofisticada não consegue compensar dados ruins. Garbage in, garbage out — GIGO. Dimensões: exatidão; completude; consistência; atualidade; unicidade; validade.

Geração de insights

Insight é uma percepção relevante obtida a partir da análise dos dados, capaz de revelar algo importante para compreensão ou decisão. Não é simplesmente "o gráfico mostra 20%". Insight seria: "Os atrasos concentram-se em três terminais e aumentam significativamente em períodos de pico."

Arquitetura de Dados

Modelagem de Dados

Modelagem de dados é o processo de representar, de maneira organizada, quais dados existem em um sistema, como eles se relacionam e quais regras devem ser respeitadas. Antes de criar tabelas em um banco de dados, precisamos responder: Quais informações o sistema precisa armazenar? Como essas informações se relacionam? Quais regras devem ser obedecidas?

Exemplo: em um sistema da Transpetro para gerenciamento de transporte de cargas, precisamos armazenar navios, caminhões, funcionários, terminais, cargas, viagens, clientes e contratos. A modelagem transforma essa necessidade de negócio em uma estrutura que posteriormente poderá virar um banco de dados.

Os três níveis de modelagem

Modelo conceitual

É a representação mais abstrata dos dados. Preocupa-se com: entidades; atributos; relacionamentos; regras de negócio. Não está preocupado com detalhes específicos do SGBD.

Exemplo: CLIENTE 1 —— N CONTRATO 1 —— N CARGA. Isso significa que um cliente pode possuir vários contratos e um contrato pode possuir várias cargas.

Importante: no modelo conceitual, não precisamos dizer VARCHAR(100), INT, DATE, DECIMAL(10,2). Esses detalhes pertencem aos níveis posteriores.

Modelo lógico

Transforma o modelo conceitual em uma estrutura mais próxima do banco de dados. Aparecem: tabelas; atributos; chaves primárias; chaves estrangeiras; tipos de relacionamento; normalização.

A relação é implementada através da chave estrangeira CONTRATO.id_cliente referenciando CLIENTE.id_cliente.

Modelo físico

É a implementação efetiva no SGBD. Entram detalhes como: tipos de dados; índices; particionamento; tablespaces; constraints; armazenamento; configuração específica do SGBD.

CREATE TABLE cliente (
  id_cliente INT PRIMARY KEY,
  nome VARCHAR(150) NOT NULL,
  cnpj VARCHAR(14) UNIQUE
);

Criação e alteração dos modelos

A modelagem não acontece apenas uma vez. Sistemas evoluem. Imagine que inicialmente o sistema possua CLIENTE (id, nome). Posteriormente surge a necessidade de armazenar o segmento do cliente. O modelo conceitual é alterado; depois o modelo lógico; e finalmente o banco:

ALTER TABLE cliente ADD segmento VARCHAR(100);

Portanto: Necessidade do negócio → Alteração conceitual → Alteração lógica → Alteração física (ALTER TABLE).

Modelo Relacional

O modelo relacional organiza os dados principalmente em relações, normalmente representadas por tabelas. Uma tabela possui linhas e colunas.

id_clientenomecidade
1PetrobrasRio de Janeiro

Linha: representa uma ocorrência/registro. Coluna: representa um atributo.

Chave primária

A Primary Key (PK) identifica unicamente cada registro. Não podemos ter id_cliente = 10 para dois clientes diferentes. A chave primária deve ser: única; identificadora; não nula.

Chave estrangeira

A Foreign Key (FK) estabelece uma relação entre tabelas. Exemplo: CLIENTE (id_cliente PK, nome); PEDIDO (id_pedido PK, id_cliente FK, valor). O campo id_cliente em PEDIDO referencia CLIENTE.

Integridade referencial

Garante que relacionamentos entre tabelas permaneçam válidos. Se tentarmos excluir o cliente 10 e existir um pedido apontando para ele, o banco pode impedir a exclusão (RESTRICT), excluir os registros relacionados (CASCADE) ou definir o relacionamento como nulo.

Normalização

Utilizada para organizar estruturas de dados e reduzir redundância, inconsistência e anomalias de inserção, atualização e exclusão.

Exemplo de problema: o telefone de João aparece várias vezes. Se João trocar de telefone, precisamos alterar vários registros, o que pode gerar inconsistência.

Primeira Forma Normal — 1FN

Busca garantir que os atributos sejam atômicos. Errado: telefone = "9999-1111, 9888-2222". Uma estrutura mais adequada poderia ser CLIENTE (id, nome) e TELEFONE (id, id_cliente, telefone).

Segunda Forma Normal — 2FN

Relacionada à dependência completa da chave primária, especialmente em relações com chaves compostas. Um atributo não deve depender apenas de parte de uma chave composta.

Terceira Forma Normal — 3FN

Procura eliminar dependências transitivas. Se id_cliente → id_cidade e id_cidade → nome_cidade, então id_cliente → nome_cidade por dependência transitiva. Estrutura normalizada: CLIENTE (id_cliente, nome, id_cidade); CIDADE (id_cidade, nome).

Metadados

São dados sobre dados. Exemplo: nome da tabela CLIENTE; coluna CNPJ; tipo VARCHAR(14); permite NULL: não; chave: UNIQUE. Em um arquivo clientes.csv, informações como "arquivo criado em 26/08/2026", "UTF-8", "separador = ;", "coluna CNPJ = texto" são metadados.

Modelagem dimensional

Muito utilizada em Business Intelligence, Data Warehouse, relatórios e análise gerencial. Trabalha com tabela fato (eventos e medidas) e tabelas dimensão (contexto).

Exemplo: FATO_TRANSPORTE (id_tempo, id_cliente, id_navio, id_terminal, quantidade, valor, peso). Dimensões: DIM_CLIENTE, DIM_NAVIO, DIM_TEMPO, DIM_TERMINAL.

Esquema estrela

DIM_CLIENTE — FATO_TRANSPORTE — DIM_NAVIO — DIM_TEMPO. É chamado de Star Schema porque visualmente lembra uma estrela.

Esquema floco de neve

No Snowflake Schema, as dimensões podem ser normalizadas. Exemplo: FATO → DIM_CLIENTE → CIDADE → ESTADO → PAÍS.

Diferença: Estrela — mais simples e geralmente mais desnormalizada. Floco de neve — dimensões mais normalizadas.

Avaliação de modelos de dados

Um modelo deve ser avaliado quanto a: consistência; integridade; normalização; redundância; desempenho; escalabilidade; segurança; aderência às regras de negócio; facilidade de manutenção.

Pergunta típica: um modelo pode estar normalizado e ainda apresentar problemas? Sim. Normalização não garante automaticamente bom desempenho, boa arquitetura, facilidade de consulta ou escalabilidade.

Engenharia reversa

É o processo de partir de um sistema existente para descobrir sua estrutura. Por exemplo: banco existente → levantamento das tabelas → relacionamentos → chaves → tipos → modelo lógico → modelo conceitual. Você recebe um banco SQL Server com 800 tabelas, sem documentação, e uma ferramenta de engenharia reversa pode identificar CLIENTE, PEDIDO, ITEM_PEDIDO, PRODUTO e gerar um diagrama ER.

SQL

SQL — Structured Query Language — é utilizada para trabalhar com bancos relacionais. Pode ser dividida em diferentes categorias.

DDL — Data Definition Language

Usada para definir estruturas. Principais comandos: CREATE, ALTER, DROP, TRUNCATE.

CREATE TABLE cliente (
  id INT PRIMARY KEY,
  nome VARCHAR(100)
);

DML — Data Manipulation Language

Manipula os dados. Principais comandos: INSERT, UPDATE, DELETE.

INSERT INTO cliente (id, nome) VALUES (1, 'João');
UPDATE cliente SET nome='José' WHERE id=1;
DELETE FROM cliente WHERE id=1;

SELECT

SELECT nome FROM cliente;
SELECT nome FROM cliente WHERE cidade='Rio de Janeiro';

JOIN

Permite combinar informações de tabelas.

SELECT c.nome, p.valor
FROM cliente c
INNER JOIN pedido p ON p.id_cliente = c.id_cliente;

INNER JOIN: retorna registros que possuem correspondência nos dois lados. LEFT JOIN: retorna todos os registros da tabela da esquerda, mesmo que não exista correspondência.

SGBD

Sistema Gerenciador de Banco de Dados é o software responsável por gerenciar bancos de dados. Exemplos: PostgreSQL; Oracle Database; Microsoft SQL Server; MySQL; MariaDB. Um SGBD normalmente oferece: armazenamento; consultas; transações; controle de concorrência; segurança; recuperação; backup; gerenciamento de usuários; integridade.

ACID

Tópico muito importante para prova. ACID significa: Atomicidade; Consistência; Isolamento; Durabilidade.

Atomicidade

Uma transação é tratada como uma unidade. Ou tudo acontece (COMMIT) ou nada acontece (ROLLBACK). Exemplo: transferência bancária de R$ 100 da conta A para a conta B — não pode acontecer apenas uma das operações.

Consistência

A transação deve levar o banco de um estado válido para outro estado válido. Se uma regra determina saldo >= 0, uma transação não deveria deixar saldo = -R$ 5.000.

Isolamento

Transações concorrentes não devem interferir indevidamente umas nas outras. O SGBD precisa controlar como elas enxergam e alteram os dados.

Durabilidade

Depois de confirmado o COMMIT, o efeito da transação deve persistir mesmo após falha do sistema.

Transações

BEGIN TRANSACTION;
UPDATE conta SET saldo = saldo - 100 WHERE id=1;
UPDATE conta SET saldo = saldo + 100 WHERE id=2;
COMMIT;
-- Se algo der errado:
ROLLBACK;

Independência de dados

Permite mudanças em determinado nível da arquitetura sem exigir alterações nos níveis superiores. Existem principalmente: independência física (alterações no armazenamento físico sem alterar o modelo lógico, ex.: alterar índice sem modificar aplicações) e independência lógica (alterações no modelo lógico sem exigir mudanças nas visões externas, quando possível).

Performance de banco de dados

Principais técnicas: índices; otimização de consultas; análise do plano de execução; particionamento; cache; atualização de estatísticas; normalização/desnormalização adequada; dimensionamento de hardware; controle de concorrência.

CREATE INDEX idx_cliente_cpf ON cliente(cpf);

Cuidado: índice não é solução mágica. Muitos índices podem ocupar espaço e aumentar o custo de INSERT, UPDATE e DELETE.

Bancos NoSQL

Bancos que não seguem necessariamente o modelo relacional tradicional. Principais categorias: chave-valor; documentos; colunas; grafos.

{
  "id": 10,
  "nome": "João",
  "cidade": "Rio de Janeiro",
  "telefones": ["9999-1111", "9888-2222"]
}

ETL

ETL: Extract, Transform, Load. Extract: extrair dados (ERP, banco SQL, CSV, API). Transform: limpar, padronizar, corrigir, agregar, converter. Load: carregar no destino (Data Warehouse).

Exemplo: RJ, Rio de Janeiro, R.J. podem ser padronizados para RIO DE JANEIRO na transformação.

Transferência de arquivos

Uma forma simples de integração: Sistema A → CSV → SFTP → Sistema B. É comum em integrações legadas. Problemas possíveis: atraso; arquivo corrompido; duplicidade; perda; incompatibilidade de formato.

Integração via banco de dados

Um sistema pode acessar dados disponibilizados por outro banco. Pode envolver: views; tabelas compartilhadas; replicação; links entre bancos; processos de carga.

Banco em memória

Banco in-memory mantém dados principalmente na memória RAM para obter alta velocidade. Exemplo: Redis. Casos de uso: cache; sessões; dados temporários; filas; respostas de alta velocidade. Atenção: RAM é muito mais rápida, mas é volátil — mecanismos de persistência podem ser utilizados conforme a solução.

Qualidade de dados

Qualidade de dados representa o grau em que os dados são adequados ao uso pretendido. Dimensões comuns: precisão; completude; consistência; atualidade; unicidade; validade. Exemplo: CPF inválido caracteriza problema de qualidade.

Dados mestres

Master Data são dados fundamentais compartilhados por diferentes processos. Exemplos: cliente; produto; fornecedor; funcionário; local. A gestão de dados mestres busca garantir uma visão consistente.

Dados de referência

Utilizados para classificar ou padronizar informações. Exemplo: UF (RJ, SP, MG, ES) ou TIPO_DOCUMENTO (CPF, CNPJ, PASSAPORTE).

Data Lake

Armazena grandes volumes de dados em diferentes formatos: CSV, JSON, logs, imagens, vídeos, dados de sensores, dados estruturados. A ideia central é armazenar dados em grande escala antes ou independentemente de uma modelagem rígida para uso analítico.

Big Data

Envolve conjuntos de dados caracterizados frequentemente pelos 5 Vs: Volume (grande quantidade); Velocidade (grande velocidade de geração/processamento); Variedade (diferentes formatos); Veracidade (confiabilidade); Valor (capacidade de gerar valor).

Gerenciamento de Projetos e Produtos

Projeto x Produto

Projeto: esforço temporário para criar um resultado único. Exemplo: construir um novo sistema de gerenciamento de cargas. Possui início, desenvolvimento e conclusão.

Produto: algo que gera valor continuamente. Exemplo: o sistema de gerenciamento de cargas, que depois de lançado continua recebendo melhorias, correções, novas funcionalidades e adaptações.

Resumindo: Projeto = esforço temporário. Produto = solução que gera valor continuamente.

Scrum

Scrum é um framework para desenvolver e sustentar produtos complexos. Trabalha com ciclos chamados Sprints, com duração fixa.

Papéis/accountabilities do Scrum

Product Owner: responsável por maximizar o valor do produto e gerenciar o Product Backlog. Scrum Master: responsável por estabelecer o Scrum e ajudar a melhorar a efetividade do Scrum Team. Developers: profissionais que criam o incremento utilizável.

Eventos Scrum

Sprint; Sprint Planning; Daily Scrum; Sprint Review; Sprint Retrospective.

Product Backlog

Lista ordenada do que pode ser necessário no produto. Exemplo: Login; Cadastro de clientes; Consulta de cargas; Dashboard; Exportação de relatórios. O Product Owner ordena o backlog buscando maximizar valor.

Incremento

Versão utilizável do produto que atende à Definition of Done. Exemplo ao final da Sprint: Login funcionando + testes realizados + segurança validada.

Kanban

Kanban é um método de gestão de fluxo de trabalho. Um quadro típico: BACKLOG | A FAZER | EM ANDAMENTO | TESTE | CONCLUÍDO.

WIP

WIP = trabalho em progresso. Exemplo: DESENVOLVIMENTO WIP LIMIT = 2 significa que no máximo duas tarefas podem estar simultaneamente nessa etapa. O objetivo é evitar excesso de trabalho iniciado e melhorar o fluxo.

SAFe

SAFe — Scaled Agile Framework — é utilizado para aplicar princípios e práticas ágeis em organizações de maior escala. Quando temos dezenas ou centenas de profissionais, precisamos coordenar estratégia, dependências e entregas.

Portfólio

Portfólio reúne iniciativas relacionadas à estratégia da organização. Exemplo: Estratégia — reduzir custos operacionais. Portfólio — automação, modernização de sistemas, analytics, IoT. A gestão de portfólio busca garantir que os investimentos estão realmente contribuindo para a estratégia.

Entregas incrementais

Em vez de esperar três anos por um sistema gigante, entregamos MVP → Versão 1 → Versão 2 → Versão 3 → Produto evoluído. Cada incremento adiciona valor.

Projetos e organização

Um projeto não existe isoladamente. Ele está inserido em uma organização: ORGANIZAÇÃO → Estratégia → Portfólio → Programas → Projetos. A estratégia define direção; os projetos devem contribuir para essa estratégia.

Programa

Grupo de projetos relacionados gerenciados de forma coordenada para obter benefícios que não seriam obtidos necessariamente pela gestão individual dos projetos. Exemplo: Programa de Transformação Digital — Projeto ERP, Projeto Data Lake, Projeto Aplicativo, Projeto Automação.

Portfólio x Programa x Projeto

Projeto: busca entregar um resultado específico. Programa: coordena projetos relacionados. Portfólio: agrupa investimentos/iniciativas para atingir objetivos estratégicos.

Macete: PROJETO → entrega. PROGRAMA → benefícios. PORTFÓLIO → estratégia.

PMO

PMO — Project Management Office — é uma estrutura organizacional que apoia e/ou governa o gerenciamento de projetos. Pode fornecer: metodologias; padrões; templates; treinamento; indicadores; governança; suporte aos gerentes.

Tipos de PMO

PMO de suporte: baixo grau de controle. Fornece orientação, modelos, treinamento, conhecimento. PMO de controle: maior grau de controle. Pode exigir padrões, metodologias, auditorias, conformidade. PMO diretivo: alto grau de controle.

Levantamento, análise e gerenciamento de requisitos

O que é um requisito?

Um requisito descreve uma necessidade, capacidade, condição ou característica que um sistema deve atender. Em termos simples: requisito é aquilo que o sistema precisa fazer ou uma condição que precisa satisfazer.

Exemplo: "O sistema deve permitir que o operador consulte a localização de uma carga." Outro: "O sistema deve permitir acesso somente a usuários autenticados."

Requisito funcional

Exemplos: RF01 — O sistema deve permitir cadastrar usuários. RF02 — consultar cargas. RF03 — gerar relatório mensal. RF04 — enviar notificação quando uma carga chegar ao destino. A pergunta básica é: O que o sistema deve fazer?

Requisito não funcional

Estabelece características, restrições ou qualidades do sistema: desempenho; segurança; disponibilidade; usabilidade; confiabilidade; escalabilidade; compatibilidade. Exemplo: "O sistema deve responder às consultas em até 2 segundos." Isso não descreve uma funcionalidade específica; descreve desempenho.

Requisitos de negócio

Representam necessidades da organização. Exemplo: aumentar a produtividade em 20%. Não é necessariamente uma função do software; é um objetivo de negócio.

Requisitos de usuário

Descrevem necessidades do usuário de maneira compreensível. Exemplo: "O operador deve conseguir visualizar as cargas em trânsito." São normalmente mais abstratos que os requisitos de sistema.

Requisitos de sistema

Mais detalhados e técnicos. Exemplo: "O sistema deverá consultar a API de rastreamento a cada 60 segundos."

Stakeholders

Partes interessadas que podem fornecer requisitos; utilizar o sistema; ser afetadas pelo sistema; financiar o projeto; regulamentar o sistema; operar o sistema. Exemplo de sistema corporativo: Diretoria, Gestores, Usuários, TI, Segurança, Auditoria, Órgãos reguladores. Cada stakeholder pode possuir necessidades diferentes.

Levantamento de requisitos

É o processo de descobrir e compreender as necessidades dos stakeholders. Também pode ser chamado de elicitação de requisitos.

Técnicas de levantamento

Entrevista

O analista conversa diretamente com os stakeholders. Vantagem: permite aprofundar informações. Desvantagem: pode sofrer influência da percepção do entrevistado.

Questionários

Úteis quando existem muitos usuários. Em vez de entrevistar 500 operadores, aplica-se um questionário.

Workshops

Reúnem vários stakeholders para discutir necessidades. São úteis para consenso; conflitos; priorização; definição colaborativa.

Brainstorming

Técnica de geração de ideias. O objetivo inicial é estimular quantidade de ideias antes da avaliação crítica.

Observação

O analista acompanha o usuário executando seu trabalho. É importante porque o usuário nem sempre consegue explicar tudo que realmente faz. Durante a observação, o analista percebe atividades que podem gerar requisitos ocultos.

Prototipação

Criar uma representação inicial do sistema para obter feedback. Ajuda a descobrir requisitos antes do desenvolvimento.

Análise de documentos

O analista examina: procedimentos; contratos; formulários; legislação; sistemas existentes; manuais; relatórios.

Engenharia reversa

Um sistema existente pode ser analisado para descobrir "Como ele realmente funciona?". Isso pode revelar requisitos e regras de negócio que não estão documentados.

Análise de requisitos

Depois de levantar informações, é necessário analisá-las. O objetivo é identificar: inconsistências; ambiguidades; conflitos; duplicidades; requisitos incompletos; requisitos inviáveis; prioridades.

Exemplo de requisito ruim

"O sistema deverá ser rápido."

Problema: o que significa rápido? 1 segundo? 2 segundos? 10 segundos? Uma versão melhor: "O sistema deverá responder a 95% das consultas em até 2 segundos." Agora temos um critério mensurável.

Ambiguidade

Um requisito é ambíguo quando pode ser interpretado de diferentes maneiras. Exemplo: "O sistema deve permitir acesso rápido." Rápido para quem? Quanto tempo? Em qual situação?

Inconsistência

Dois requisitos entram em conflito. Exemplo: R1: o sistema deve permitir acesso externo. R2: o sistema não deve permitir acesso externo. Não podem coexistir sem uma regra adicional.

Priorização de requisitos

Técnica conhecida: MoSCoW. Must have: obrigatório. Should have: importante, mas não absolutamente obrigatório. Could have: desejável. Won't have: não será implementado naquele momento.

Exemplo: Must — consultar carga. Should — receber alertas. Could — personalizar dashboard. Won't — tema escuro na primeira versão.

Critérios de qualidade de requisitos

Um bom requisito deve ser: claro; necessário; consistente; verificável; viável; rastreável; não ambíguo.

Rastreabilidade

Permite relacionar: Necessidade → Requisito → Projeto → Código → Teste → Resultado. Exemplo: REQ-001 → Caso de uso UC-001 → Classe LoginService → Teste TST-001. Isso facilita impacto de mudanças e auditoria.

Gerenciamento de requisitos

Depois de levantados, os requisitos precisam ser controlados durante todo o ciclo de vida. Isso envolve: documentação; priorização; versionamento; rastreabilidade; controle de mudanças; validação; acompanhamento.

Mudança de requisito

Uma alteração pode impactar: arquitetura; banco de dados; APIs; segurança; cronograma; custos; testes. Por isso, mudança de requisito deve ser analisada.

Análise de impacto

Antes de aceitar uma mudança: Mudança → Impacto no sistema → Impacto no prazo → Impacto no custo → Impacto nos riscos → Decisão.

Ciclo de vida de sistemas

O que é ciclo de vida?

Representa as etapas pelas quais um sistema passa desde sua concepção até sua retirada. Uma representação clássica: Necessidade → Requisitos → Análise → Projeto → Implementação → Testes → Implantação → Manutenção → Retirada.

Paradigma cascata

No modelo Waterfall/Cascata, as fases são executadas predominantemente de maneira sequencial. Vantagem: maior previsibilidade e documentação. Desvantagem: mudanças tardias podem ser caras.

Exemplo de cascata

Imagine um sistema regulatório com requisitos altamente estáveis. A organização pode definir: Requisitos → Projeto → Desenvolvimento → Testes → Implantação.

Modelo incremental

O sistema é desenvolvido em partes: Incremento 1 → Incremento 2 → Incremento 3 → Incremento 4. Cada incremento acrescenta funcionalidade.

Modelo iterativo

O sistema evolui através de ciclos sucessivos: Versão inicial → Feedback → Melhoria → Nova versão → Feedback.

Iterativo x incremental

Iterativo: busca aprimorar progressivamente algo existente. Incremental: adiciona novas partes ou funcionalidades. Um processo pode ser iterativo e incremental.

Modelo espiral

Combina desenvolvimento iterativo com forte foco em riscos. Planejamento → Análise de riscos → Desenvolvimento → Avaliação → Novo ciclo. É especialmente útil em sistemas complexos e de alto risco.

Prototipação

Um protótipo é criado para explorar requisitos ou solução. Pode ser descartável ou evolucionário.

Métodos ágeis

Características: ciclos curtos; feedback frequente; adaptação; colaboração; entrega incremental; foco no valor. Exemplos: Scrum; Kanban.

Modelo híbrido

Combina práticas preditivas e adaptativas. Exemplo: arquitetura — planejamento inicial; desenvolvimento — Scrum; governança — controles tradicionais.

Paradigma estruturado

O que é análise estruturada?

É uma abordagem tradicional de análise de sistemas baseada principalmente em: processos; fluxos de dados; funções; entradas e saídas.

DFD — Diagrama de Fluxo de Dados

Representa o fluxo de dados dentro do sistema. Elementos comuns: entidade externa; processo; fluxo de dados; depósito de dados.

Processo

Representa uma transformação de dados. Exemplo: Dados do pedido → [Validar Pedido] → Pedido validado.

Entidade externa

É uma fonte ou destino externo ao sistema. Exemplo: Cliente, Fornecedor, Banco, Operador.

Dicionário de dados

Descreve os elementos de dados utilizados no sistema. Exemplo: CPF — tipo: texto; tamanho: 11; obrigatório: sim.

Diagrama de contexto

Representa o sistema de maneira macro e suas interações externas.

Paradigma orientado a objetos

O que é orientação a objetos?

Paradigma baseado na representação do sistema por meio de objetos, que possuem: estado; comportamento; identidade.

Classe

Classe é uma abstração que define características e comportamentos de objetos.

Objeto

É uma instância de uma classe. Classe: Carga. Objeto: Carga 10234.

Encapsulamento

Consiste em esconder detalhes internos e controlar o acesso ao estado do objeto. Em vez de permitir conta.saldo = -999999, a classe pode controlar.

Herança

Permite criar uma classe baseada em outra. Veículo → Caminhão. Caminhão pode herdar características de Veículo.

Polimorfismo

Permite que objetos diferentes respondam de maneira própria a uma mesma operação/interface. Exemplo: calcularFrete() pode existir em Caminhão, Navio e Trem, cada classe implementando o cálculo de forma diferente.

Abstração

Representar os aspectos relevantes de uma entidade ignorando detalhes desnecessários.

UML

A UML — Unified Modeling Language — é uma linguagem de modelagem. Ela não é uma metodologia de desenvolvimento. Pegadinha: UML = metodologia? Não. UML é uma linguagem de modelagem.

Diagrama de casos de uso

Representa interações entre atores e sistema. Exemplo: Operador → Consultar Carga.

Ator

É um papel desempenhado por uma entidade externa que interage com o sistema. Pode ser: pessoa; sistema; dispositivo. Atenção: ator não é necessariamente uma pessoa.

Caso de uso

Representa uma funcionalidade do ponto de vista do ator. Exemplos: cadastrar carga; consultar carga; emitir relatório.

Diagrama de classes

Representa: classes; atributos; operações; relacionamentos. Exemplo: Carga (código, peso, destino; registrar(), rastrear()).

Associação

Representa relacionamento entre classes. Cliente — Pedido. Um cliente realiza pedidos.

Composição

Representa uma relação forte de todo-parte. Exemplo: Pedido — ItemPedido. Se o pedido deixa de existir, os itens pertencentes àquele pedido também podem deixar de existir.

Agregação

Também representa relação todo-parte, porém mais fraca. Exemplo: Equipe — Funcionário. O funcionário pode existir independentemente da equipe.

Diagrama de sequência

Mostra a interação entre objetos ao longo do tempo.

Verificação, validação e testes

Verificação x validação

Verificação: Estamos construindo o produto corretamente? Busca verificar se o software está de acordo com especificações e artefatos definidos. Validação: Estamos construindo o produto correto? Busca verificar se o produto atende às necessidades reais dos usuários e stakeholders.

Frase para memorizar: Verificação = produto conforme especificação. Validação = produto adequado à necessidade.

Teste de unidade

Testa pequenas unidades do software. Exemplo: calcularFrete() pode ser testado isoladamente.

Teste de integração

Verifica a interação entre componentes: Frontend → API → Banco de dados.

Teste de sistema

Avalia o sistema como um todo: Login; Cadastro; Relatórios.

Teste de aceitação

Avalia se o sistema atende aos critérios de aceitação e necessidades relevantes do negócio. Pode envolver usuários ou representantes do negócio.

Teste funcional

Verifica se determinada funcionalidade apresenta o comportamento esperado. Exemplo: ao informar usuário e senha válidos, o sistema deve permitir acesso.

Teste não funcional

Avalia características como: desempenho; segurança; usabilidade; disponibilidade; escalabilidade.

Teste de desempenho

Exemplo: o sistema suporta 5.000 usuários simultâneos?

Teste de carga

Verifica comportamento sob determinada carga esperada.

Teste de estresse

Submete o sistema a condições superiores às esperadas para observar seu comportamento. Carga normal: 5.000 usuários; teste de estresse: 20.000 usuários.

Teste de regressão

Verifica se mudanças introduziram defeitos em funcionalidades que anteriormente funcionavam. Alteramos a tela de login e depois verificamos cadastro, relatórios e consulta para garantir que nada foi quebrado.

Teste exploratório

O testador explora o sistema simultaneamente ao aprendizado e à elaboração de testes, sem script rígido.

Teste caixa-preta

O testador avalia entradas e saídas sem necessariamente conhecer a implementação interna.

Teste caixa-branca

Considera a estrutura interna do software. Pode analisar: caminhos; condições; comandos; cobertura de código.

Teste caixa-cinza

Combina características das abordagens caixa-preta e caixa-branca. O testador possui algum conhecimento da estrutura interna.

Testes automatizados

São executados por ferramentas. Podem fazer parte de uma pipeline CI/CD.

Pirâmide de testes

Em geral: muitos testes unitários; menos testes de integração; poucos testes end-to-end. A lógica é buscar feedback rápido e custo menor nos níveis inferiores.

Defeito, erro e falha

Erro: ação humana incorreta. Defeito: problema introduzido no software ou artefato. Falha: comportamento incorreto observado durante a execução.

Ambientes de desenvolvimento

O que é ambiente de desenvolvimento?

Conjunto de ferramentas, infraestrutura, configurações e serviços utilizados para desenvolver e executar software. Pode envolver: IDE; compiladores; SDK; bibliotecas; banco de dados; servidores; sistemas de controle de versão; ferramentas de testes; CI/CD.

IDE

IDE — Integrated Development Environment. Exemplos: Visual Studio Code; IntelliJ IDEA; Eclipse; Visual Studio; Android Studio.

Ambiente local

É o ambiente utilizado pelo desenvolvedor.

Ambiente de desenvolvimento

Utilizado para integração e desenvolvimento da aplicação. Pode ser compartilhado pela equipe.

Ambiente de testes

Utilizado para execução de testes. Pode possuir dados controlados, configurações específicas e ferramentas de automação.

Homologação

Ambiente utilizado para validar a solução antes da produção.

Produção

É o ambiente utilizado pelos usuários reais. Alterações em produção normalmente possuem maior risco.

Separação de ambientes

Boa prática: evitar que desenvolvimento e produção sejam o mesmo ambiente. DESENVOLVIMENTO → HOMOLOGAÇÃO → PRODUÇÃO.

Controle de versão

Ferramentas como Git permitem: histórico; branches; merge; rollback; colaboração.

Integração contínua — CI

Integração frequente de código com automação de build e testes. Reduz problemas de integração e fornece feedback rápido.

Continuous Delivery e Continuous Deployment

Continuous Delivery: mantém o software pronto para implantação, com decisão manual de quando publicar. Continuous Deployment: implanta automaticamente em produção após passar pelos estágios do pipeline.

DevOps

DevOps busca aproximar: DESENVOLVIMENTO + OPERAÇÕES. Objetivos: reduzir tempo de entrega; aumentar confiabilidade; automatizar; melhorar colaboração; obter feedback rápido.

Containers

Containers empacotam aplicação e dependências em uma unidade executável. Docker é uma tecnologia amplamente associada a containers.

Gerenciamento de Projetos e Produtos

Framework Scrum

O que é Scrum?

Scrum é um framework utilizado para desenvolver, entregar e sustentar produtos complexos. Um ponto importante: Scrum não é uma metodologia prescritiva que determina exatamente como toda a equipe deve desenvolver o produto. Ele fornece uma estrutura com: responsabilidades/accountabilities; eventos; artefatos; compromissos; regras. A equipe utiliza essa estrutura e adapta suas práticas ao contexto.

Exemplo: a Transpetro pode trabalhar de maneira incremental:

  • Sprint 1 → Login + usuários
  • Sprint 2 → Cadastro de cargas
  • Sprint 3 → Rastreamento
  • Sprint 4 → Dashboard
  • Sprint 5 → Melhorias

Os três pilares do Scrum

  1. Transparência
  2. Inspeção
  3. Adaptação

Transparência

As informações relevantes devem estar visíveis e compreensíveis. Exemplo: o Product Backlog deve permitir que as pessoas entendam o que está sendo considerado para o produto. Se um projeto está atrasado, esconder essa informação prejudica a tomada de decisão.

Inspeção

O trabalho e os resultados devem ser avaliados frequentemente. Durante uma Sprint, a equipe pode descobrir que determinada solução não funciona como esperado, e a inspeção permite identificar isso antes que o problema cresça.

Adaptação

Quando a inspeção identifica um problema ou uma mudança necessária, o trabalho deve ser adaptado.

Valores do Scrum

  1. Compromisso
  2. Foco
  3. Abertura
  4. Respeito
  5. Coragem

Scrum Team

O Scrum Team é formado por: Product Owner; Scrum Master; Developers. Não são três departamentos separados. É uma equipe coesa que trabalha em direção a um objetivo comum.

Product Owner

O Product Owner (PO) é responsável por maximizar o valor do produto resultante do trabalho do Scrum Team. Uma das principais responsabilidades é gerenciar efetivamente o Product Backlog, o que envolve: desenvolver e comunicar o Product Goal; criar e comunicar itens do Product Backlog; ordenar os itens; garantir que o Product Backlog seja transparente, visível e compreensível.

Atenção: o Product Owner não é simplesmente o "chefe dos desenvolvedores".

Scrum Master

O Scrum Master é responsável por estabelecer o Scrum conforme definido pelo framework e ajudar a melhorar a efetividade do Scrum Team. Atua como facilitador; coach; agente de melhoria; removedor de impedimentos; apoiador da adoção correta do Scrum.

Pegadinha: Scrum Master = gerente tradicional da equipe? Errado. Scrum Master não é necessariamente chefe hierárquico.

Developers

São os profissionais responsáveis por criar qualquer aspecto de um incremento utilizável a cada Sprint. Podem incluir desenvolvedores; analistas; designers; testers; especialistas em dados; profissionais de infraestrutura. O termo Developers no Scrum não significa necessariamente apenas programadores.

Sprint

A Sprint é um período de duração fixa de até um mês em que um Incremento de valor é criado.

Sprint Goal

É o objetivo da Sprint. Exemplo: "Permitir que clientes acompanhem suas cargas em tempo real."

Product Backlog

É uma lista ordenada e emergente do que é necessário para melhorar o produto. Pode conter funcionalidades; melhorias; correções; requisitos; experimentos; necessidades técnicas.

Product Goal

Representa o objetivo de longo prazo para o produto. Exemplo: "Disponibilizar uma plataforma integrada de acompanhamento logístico."

Sprint Backlog

É composto por: Sprint Goal; itens do Product Backlog selecionados para a Sprint; plano de ação para entregar o Incremento.

Incremento

É uma versão utilizável do produto que atende à Definition of Done.

Definition of Done

Representa uma descrição formal do estado do Incremento quando ele atende aos critérios de qualidade exigidos. Exemplo: código desenvolvido; code review; testes automatizados; teste funcional; segurança validada; documentação. Pegadinha: "Terminei de programar" ≠ Done.

Eventos Scrum

Sprint; Sprint Planning; Daily Scrum; Sprint Review; Sprint Retrospective.

Sprint Planning

Trata três temas: Por quê? Definição do Sprint Goal. O quê? Quais itens do Product Backlog serão considerados. Como? Como o trabalho será realizado.

Daily Scrum

Evento de 15 minutos para os Developers. Objetivo: inspecionar o progresso em direção ao Sprint Goal e adaptar o Sprint Backlog conforme necessário. Pegadinha: Daily Scrum não é reunião para o gerente controlar cada funcionário.

Sprint Review

Realizada para inspecionar o resultado da Sprint e determinar adaptações futuras. Participam o Scrum Team e stakeholders relevantes. É uma oportunidade de obter feedback.

Sprint Retrospective

Tem como objetivo planejar maneiras de aumentar qualidade e efetividade. Perguntas típicas: O que funcionou? O que não funcionou? Como podemos melhorar?

Kanban

O que é Kanban?

Kanban é um método para gerenciar e melhorar o fluxo de trabalho. Foco em: visualizar o trabalho; limitar trabalho em progresso; gerenciar fluxo; tornar políticas explícitas; estabelecer ciclos de feedback; melhorar continuamente.

Lead Time

Tempo desde o início da solicitação até sua entrega. Exemplo: solicitação 01/08 → entrega 10/08 → Lead Time: 9 dias.

Tempo necessário para uma tarefa percorrer uma etapa ou fluxo de trabalho, conforme definição adotada. Em muitos contextos: início do trabalho até conclusão.

Projeto x Produto

O que é projeto?

Esforço temporário empreendido para criar um produto, serviço ou resultado único. Exemplo: implementar um novo sistema de gestão de cargas. Possui início, desenvolvimento e conclusão.

O que é produto?

Algo criado para gerar valor e que pode evoluir continuamente. Exemplo: plataforma de gerenciamento de cargas. Depois do lançamento: versão 1 → feedback → versão 2 → novas funcionalidades → versão 3.

Diferença de mentalidade

Gestão de projeto: estamos dentro do prazo? do orçamento? o escopo foi entregue? Gestão de produto: o usuário está obtendo valor? o produto resolve o problema? qual métrica demonstra sucesso? o produto deve continuar existindo dessa forma?

Exemplo

Uma empresa desenvolve um aplicativo. O projeto foi um sucesso (prazo, orçamento, escopo), mas depois descobre-se que os usuários não utilizam o aplicativo. O projeto pode ser considerado bem executado; o produto pode ser considerado um fracasso.

Agilidade em escala e SAFe

Por que agilidade em escala?

Scrum funciona muito bem para uma equipe. Mas imagine 50 equipes, 500 pessoas, vários produtos, vários departamentos, fornecedores, arquitetura corporativa. Precisamos coordenar: estratégia; orçamento; arquitetura; dependências; produtos; equipes; releases. É nesse contexto que entram abordagens como o SAFe.

O que é SAFe?

SAFe — Scaled Agile Framework — é um framework para aplicar princípios Lean, Agile e DevOps em escala organizacional. Busca conectar: Estratégia → Portfólio → Produtos → Soluções → Equipes.

Lean

O pensamento Lean busca maximizar valor e reduzir desperdícios.

Agile

Agilidade enfatiza: feedback rápido; adaptação; entregas incrementais; colaboração; foco no valor.

DevOps

DevOps aproxima desenvolvimento e operações. A automação reduz tempo e erros.

Agile Release Train — ART

É uma estrutura de longo prazo que reúne equipes e stakeholders para entregar valor de maneira contínua.

Program Increment — PI

Representa um período durante o qual um Agile Release Train entrega valor incremental. Cada iteração produz resultados.

Entrega incremental

Em vez de 12 meses → sistema completo, podemos fazer PI 1 → Cadastro; PI 2 → Rastreamento; e assim por diante.

Gestão de portfólio

Responde a uma pergunta fundamental: Estamos investindo nas iniciativas certas? A organização precisa analisar: estratégia; valor; risco; capacidade; dependências; retorno esperado.

PMBOK 7ª edição

O que é PMBOK?

PMBOK — Project Management Body of Knowledge — é um guia de conhecimentos e boas práticas de gerenciamento de projetos publicado pelo PMI. A 7ª edição trouxe uma mudança significativa na forma de organizar o conhecimento.

PMBOK 6 x PMBOK 7

Estrutura tradicional: grupos de processos; áreas de conhecimento. PMBOK 7: princípios + domínios de desempenho + sistemas de entrega de valor. Isso não significa que os processos tradicionais deixaram de existir.

Sistema de entrega de valor

Projetos não devem ser vistos isoladamente. Fazem parte de um sistema maior: Estratégia → Portfólio → Programa/Projeto → Entrega → Resultado → Benefício → Valor.

Princípios do PMBOK 7

Administração responsável; equipe; stakeholders; valor; pensamento sistêmico; liderança; qualidade; complexidade; risco; adaptabilidade e resiliência; mudança.

Valor

O projeto não deve ser avaliado somente pelo fato de ter produzido entregas. Entrega ≠ necessariamente valor.

Stakeholders

São pessoas, grupos ou organizações que podem afetar, ser afetados ou perceber-se afetados pelo projeto.

Domínios de desempenho

  1. Stakeholders
  2. Equipe
  3. Abordagem de desenvolvimento e ciclo de vida
  4. Planejamento
  5. Trabalho do projeto
  6. Entrega
  7. Medição
  8. Incerteza

Projetos e a organização

Estrutura organizacional

Classificação tradicional: funcional; matricial; projetizada.

Organização funcional

A organização é dividida por departamentos. O gerente funcional possui grande autoridade. O gerente de projeto pode ter autoridade limitada.

Organização projetizada

O projeto é o centro da organização. O gerente de projeto tende a possuir maior autoridade.

Organização matricial

Combina características funcional e projetizada. O profissional pode responder a: gerente funcional + gerente de projeto. Isso pode gerar conflitos de autoridade; disputa de recursos; necessidade de negociação.

Matriz fraca, balanceada e forte

Fraca: maior poder do gerente funcional. Balanceada: autoridade relativamente compartilhada. Forte: maior autoridade do gerente de projeto.

Escritório de Projetos — PMO

PMO — Project Management Office — é uma estrutura organizacional que apoia projetos, programas e/ou portfólios. Pode atuar em: padronização; governança; treinamento; indicadores; metodologia; acompanhamento; auditoria; suporte.

PMO de suporte

Fornece apoio, com baixo grau de controle.

PMO de controle

Possui maior autoridade. Pode exigir metodologia, templates obrigatórios, indicadores, auditorias.

PMO diretivo

Alto grau de controle sobre os projetos.

Projeto, programa e portfólio

PROJETO → entrega específica. PROGRAMA → benefícios coordenados. PORTFÓLIO → alinhamento estratégico.

Processos de gerenciamento de projetos

O que é um processo?

Conjunto de atividades relacionadas que transforma entradas em resultados. Exemplo: Requisito → Análise → Desenvolvimento → Teste → Produto.

Grupos de processos

  1. Iniciação;
  2. Planejamento;
  3. Execução;
  4. Monitoramento e Controle;
  5. Encerramento.

Iniciação

Objetivo: autorizar formalmente o projeto. Exemplos: definir objetivo; identificar stakeholders; justificar projeto; elaborar termo de abertura.

Termo de abertura

O Project Charter formaliza a existência do projeto e concede autoridade para seu gerenciamento. Pode conter: objetivo; justificativa; requisitos de alto nível; riscos iniciais; premissas; restrições; gerente do projeto; patrocinador.

Planejamento

Define como o projeto será executado: escopo; cronograma; custos; qualidade; recursos; comunicação; riscos.

Execução

Realização do trabalho: desenvolver; testar; integrar; treinar; implantar.

Monitoramento e Controle

Verifica se o projeto está seguindo o planejado. Exemplo: Planejado R$ 500 mil; Real R$ 700 mil → desvio de custo.

Controle integrado de mudanças

Mudanças são normais. Porém, é necessário avaliar impacto no escopo; prazo; custo; qualidade; riscos; recursos.

Encerramento

O projeto é formalmente concluído. Pode envolver: aceite; encerramento de contratos; documentação; arquivamento; lições aprendidas; liberação de recursos.

Áreas de conhecimento

Embora a 7ª edição do PMBOK tenha mudado a estrutura principal do guia, o edital menciona explicitamente áreas de conhecimento. Por isso, para concurso, é importante dominar a estrutura tradicional.

Integração

Coordena os diferentes elementos do projeto.

Escopo

Define e controla o que está e o que não está incluído no projeto.

Cronograma

Gerencia o tempo: atividades; duração; dependências; marcos; sequenciamento.

Custos

Gerencia estimativas; orçamento; controle dos gastos.

Qualidade

Busca garantir que as entregas atendam aos requisitos e expectativas relevantes.

Recursos

Inclui recursos humanos; físicos; tecnológicos; materiais.

Comunicações

Define quem precisa receber informação; qual informação; quando; como; em qual formato.

Riscos

Risco é uma condição ou evento incerto que, se ocorrer, pode afetar os objetivos do projeto.

Aquisições

Relacionadas à contratação de produtos, serviços ou fornecedores externos.

Stakeholders

Gerencia o relacionamento com partes interessadas.

Visão geral da Lógica Matemática

A Lógica Matemática é o ramo que estuda princípios e métodos utilizados para determinar se determinados raciocínios são válidos ou inválidos, independentemente de opiniões ou interpretações subjetivas.

Em provas, a lógica normalmente envolve: proposições; valores-verdade; conectivos lógicos; fórmulas; tabelas-verdade; equivalências; argumentos; regras de inferência; predicados; quantificadores; sistemas dedutivos; decidibilidade.

A ideia central pode ser resumida assim: a lógica não pergunta se uma afirmação é verdadeira no mundo real; ela analisa a estrutura do raciocínio.

Proposições

Uma proposição é uma sentença declarativa que pode receber exatamente um dos seguintes valores: Verdadeiro (V) ou Falso (F). Ela não pode ser simultaneamente verdadeira e falsa dentro da mesma interpretação.

Exemplos: "O Brasil está na América do Sul." (proposição verdadeira). "2 + 2 = 5." (proposição falsa). "O sistema está indisponível." (pode ser proposição, se o contexto permitir atribuir V ou F).

O que não é proposição?

Perguntas

"Qual é o horário da reunião?" Não é proposição.

Ordens

"Feche o sistema." Não é proposição.

Exclamações

"Que sistema excelente!" Não constitui proposição lógica.

Sentenças abertas

"x + 2 = 5". Enquanto o valor de x não for conhecido, é sentença aberta, não proposição. Quando estabelecemos x = 3, passamos a ter "3 + 2 = 5" — agora proposição verdadeira.

Proposições simples e compostas

Proposição simples

Não possui conectivo lógico. Exemplo: p: "O servidor está ativo."

Formada pela combinação de proposições utilizando conectivos lógicos. Exemplo: p ^ q.

Precedência dos conectivos

Ordem convencional: ¬; ∧; ∨; →; ↔. Os parênteses podem alterar essa ordem.

Teoria dos argumentos

Um argumento é uma estrutura composta por premissas e conclusão. Exemplo: Premissa 1: Todo analista é funcionário. Premissa 2: Carlos é analista. Conclusão: Carlos é funcionário.

Formalmente: P1, P2 ∴ C. O símbolo ∴ significa "portanto".

Validade de um argumento

Um argumento é válido quando é impossível que: todas as premissas sejam verdadeiras e a conclusão seja falsa. Um argumento pode ser válido mesmo que suas premissas sejam falsas. A validade depende da estrutura lógica, não da realidade das afirmações.

Exemplo de argumento válido

Se o servidor está ativo, então o sistema responde. O servidor está ativo. Logo, o sistema responde. Formalmente: p → q, p ∴ q. Essa forma é conhecida como Modus Ponens.

Modus Ponens

Estrutura: p → q; p; ∴ q. Exemplo: Se o backup foi executado, os dados foram copiados. O backup foi executado. Logo, os dados foram copiados. É válido.

Modus Tollens

Estrutura: p → q; ¬q; ∴ ¬p. Exemplo: Se o servidor está funcionando, então o sistema responde. O sistema não responde. Logo, o servidor não está funcionando. A estrutura é válida.

Falácias importantes

Afirmação do consequente

Estrutura: p → q; q; ∴ p. Isso é inválido. Exemplo: Se o servidor está ativo, então o sistema responde. O sistema responde. Logo, o servidor está ativo. Pode haver outra razão para o sistema responder.

Negação do antecedente

Estrutura: p → q; ¬p; ∴ ¬q. Também é inválida. Exemplo: Se o usuário está conectado à VPN, então consegue acessar o sistema. O usuário não está conectado à VPN. Logo, não consegue acessar o sistema. Ele pode estar conectado diretamente à rede corporativa.

Argumentos e tabela-verdade

Um argumento pode ser testado utilizando tabela-verdade. Se não existir linha em que todas as premissas são V e a conclusão é F, o argumento é válido. Regra fundamental: argumento válido = não existe interpretação com premissas verdadeiras e conclusão falsa.

Lógica sentencial

A lógica sentencial, também chamada de lógica proposicional, trabalha com proposições inteiras. Utilizamos letras como p, q, r, s. Exemplo: p = "O servidor está ativo."; q = "O banco está disponível." Podemos criar: p ∧ q ou p → q. A lógica sentencial não analisa internamente a estrutura de uma proposição.

Lógica de predicados de primeira ordem

A lógica de predicados permite representar estruturas internas das afirmações. Trabalha com: indivíduos; propriedades; relações; variáveis; quantificadores. Exemplo: "João é analista." pode ser representado por Analista(João). Aqui Analista é o predicado e João é o indivíduo.

Predicados

Um predicado expressa uma propriedade ou relação. Propriedade: Analista(João). Relação: Gerencia(João, Maria).

Variáveis

Em vez de utilizar apenas indivíduos específicos, podemos usar variáveis. Exemplo: Analista(x) significa "x é analista".

Quantificador universal — ∀

O símbolo ∀ significa "para todo". Exemplo: Todo analista é funcionário. Formalmente: ∀x (Analista(x) → Funcionario(x)). Lê-se: "Para todo x, se x é analista, então x é funcionário."

Quantificador existencial — ∃

O símbolo ∃ significa "existe pelo menos um". Exemplo: Existe um analista que trabalha no projeto. Formalmente: ∃x (Analista(x) ∧ TrabalhaNoProjeto(x)).

Negação dos quantificadores

Negação do universal: ¬∀x P(x) equivale a ∃x ¬P(x). Ou seja, "Não é verdade que todos são P" equivale a "Existe pelo menos um que não é P."

Negação do existencial: ¬∃x P(x) equivale a ∀x ¬P(x). Ou seja, "Não existe nenhum P" equivale a "Todos não são P."

Exemplo prático

Afirmação: "Todos os sistemas possuem backup." Formalmente: ∀x (Sistema(x) → PossuiBackup(x)). Negação: "Existe pelo menos um sistema que não possui backup." Formalmente: ∃x (Sistema(x) ∧ ¬PossuiBackup(x)).

Regras de formação de fórmulas

Determinam quais expressões podem ser consideradas fórmulas bem-formadas. Na lógica proposicional: uma proposição atômica é uma fórmula; se p é fórmula, ¬p é fórmula; se p e q são fórmulas, então p ∧ q, p ∨ q, p → q, p ↔ q também são fórmulas. Exemplo válido: (p ∧ q) → r.

Fórmulas malformadas

Uma expressão como p ∧ → q não segue as regras de formação. Outro exemplo: (p ∨ q — parêntese não fechado.

Sintaxe × semântica

Sintaxe: preocupa-se com a forma da expressão. Semântica: preocupa-se com o significado/valor-verdade da expressão.

Sistemas dedutivos

Conjunto organizado de regras utilizado para derivar conclusões a partir de premissas ou axiomas. Premissas + regras de inferência → conclusão. Entre as regras clássicas: Modus Ponens; Modus Tollens; introdução da conjunção; eliminação da conjunção; introdução da disjunção.

Modus Ponens como regra dedutiva

Temos p → q e p. Podemos deduzir q.

Eliminação da conjunção

Se temos p ∧ q, podemos concluir p ou q.

Introdução da conjunção

Se temos p e q, podemos concluir p ∧ q.

Equivalência lógica

Duas fórmulas são logicamente equivalentes quando possuem o mesmo valor-verdade em todas as interpretações. Representamos p ≡ q.

Equivalência muito importante: p → q ≡ ¬p ∨ q.

Outras equivalências importantes

Dupla negação: ¬(¬p) ≡ p.

Leis de De Morgan:

  • ¬(p ∧ q) ≡ ¬p ∨ ¬q
  • ¬(p ∨ q) ≡ ¬p ∧ ¬q

Condicional e contrapositiva

Equivalência fundamental: p → q é equivalente a ¬q → ¬p (contrapositiva). Exemplo: Original — Se o sistema está ativo, então responde. Contrapositiva — Se o sistema não responde, então não está ativo.

Cuidado com a recíproca

A recíproca de p → q é q → p. Mas p → q ≠ q → p em geral. Exemplo: Se algo é um cachorro, então é um animal. Isso não significa: Se algo é um animal, então é um cachorro.

Valores-verdade

Na lógica clássica, uma proposição pode assumir V ou F.

Funções de avaliação

Atribuem valores-verdade às proposições. Exemplo: v(p) = V, v(q) = F. Então v(p ∧ q) = F e v(p ∨ q) = V.

Tabela-verdade

Apresenta todas as possíveis combinações de valores-verdade. Para n proposições, existem 2ⁿ combinações.

  • 1 proposição: 2¹ = 2 linhas
  • 2 proposições: 2² = 4 linhas
  • 3 proposições: 2³ = 8 linhas
  • 4 proposições: 2⁴ = 16 linhas

Atenção para a prova: se a fórmula tem p, q, r e s, serão 2⁴ = 16 linhas.

Decidibilidade da lógica sentencial

A lógica sentencial clássica é decidível. Existe um procedimento finito que permite determinar se uma fórmula possui determinada propriedade lógica. Por exemplo, podemos usar tabela-verdade para determinar se uma fórmula é tautomógica.

Satisfatibilidade

Uma fórmula é satisfatível quando existe pelo menos uma interpretação que a torna verdadeira. Exemplo: p ∧ q é satisfatível porque p = V e q = V torna a fórmula verdadeira.

Fórmula não satisfatível

p ∧ ¬p. Não existe nenhuma atribuição que torne essa fórmula verdadeira. É insatisfatível — corresponde a uma contradição.

Relação entre tautologia e satisfatibilidade

Toda tautologia é satisfatível. Mas nem toda fórmula satisfatível é uma tautologia. Exemplo: p é satisfatível, mas não é tautologia.

Argumento e tautologia

Um argumento P1, P2, ..., Pn ∴ C é válido se a fórmula (P1 ∧ P2 ∧ ... ∧ Pn) → C for uma tautologia.

Exemplo: p → q, p ∴ q. A fórmula [(p → q) ∧ p] → q é uma tautologia. Logo, o argumento é válido.

Consistência

Um conjunto de proposições é consistente quando existe pelo menos uma interpretação na qual todas sejam verdadeiras simultaneamente. p e q são consistentes. p e ¬p são inconsistentes.

Exemplo completo — contexto de TI

Considere: p = "O usuário está autenticado."; q = "O usuário possui autorização."; r = "O usuário poderá acessar o sistema." A frase "Se o usuário está autenticado e possui autorização, então poderá acessar o sistema" pode ser representada como (p ∧ q) → r.

Pegadinhas clássicas de prova

  1. "ou": nem sempre significa exclusivo. Na lógica convencional, p ∨ q representa OU inclusivo.
  2. Condicional: p → q não é falsa quando p e q são falsos. Só é falsa em V → F.
  3. Negação de "todos": a negação de "Todos os sistemas estão funcionando" é "Existe pelo menos um sistema que não está funcionando", e não "Nenhum sistema está funcionando".
  4. Recíproca: de p → q não podemos concluir q → p.
  5. Contrapositiva: de p → q podemos concluir a equivalência ¬q → ¬p.
  6. Validade: argumento válido não significa necessariamente que todas as premissas sejam verdadeiras.
  7. Proposição: perguntas, ordens e sentenças abertas normalmente não são proposições.

Como resolver questões de lógica na prova

  1. Identifique as proposições — separe as frases em p, q, r...
  2. Identifique os conectivos — procure: não; e; ou; se... então; se e somente se.
  3. Traduza para símbolos — exemplo: "Se p, então q" vira p → q.
  4. Observe a estrutura — conjunção? condicional? bicondicional?
  5. Se necessário, monte a tabela-verdade — 2ⁿ linhas.
  6. Procure a pegadinha — condicional; negação de quantificadores; recíproca; contrapositiva; OU inclusivo × exclusivo; validade de argumentos.

O que mais merece memorização para a prova

  1. Tabelas dos conectivos — especialmente p ∧ q, p ∨ q, p → q, p ↔ q.
  2. Condicional — V → F = F; todos os demais casos verdadeiros.
  3. Modus Ponens e Modus Tollens — p → q, p ∴ q; p → q, ¬q ∴ ¬p.
  4. Falácias — afirmação do consequente; negação do antecedente.
  5. Quantificadores — ∀ = todo; ∃ = existe.
  6. Negação dos quantificadores — ¬∀x P(x) ≡ ∃x ¬P(x); ¬∃x P(x) ≡ ∀x ¬P(x).
  7. Tautologia, contradição e contingência.
  8. Quantidade de linhas — n proposições → 2ⁿ linhas.

Segurança da Informação

Material de Estudo — Transpetro · Ênfase 5

Visão geral

Segurança da Informação tem como objetivo proteger: informações; sistemas; redes; dispositivos; aplicações; usuários; serviços; infraestrutura. A tríade clássica é: Confidencialidade + Integridade + Disponibilidade — conhecida como CIA (Confidentiality, Integrity and Availability).

Confidencialidade

Garante que a informação seja acessível somente por pessoas ou sistemas autorizados. Exemplo: um funcionário do setor financeiro não deve conseguir consultar informações sigilosas de RH simplesmente porque possui acesso à rede corporativa.

Integridade

Garante que a informação não seja alterada indevidamente. Exemplo: um atacante modifica o valor de uma ordem de pagamento.

Disponibilidade

Garante que informações e serviços estejam disponíveis quando necessários. Exemplo: um ataque DDoS derruba o portal de uma empresa.

Segurança física e lógica

Segurança física

Protege os recursos físicos da organização: servidores; datacenters; computadores; racks; cabeamento; dispositivos de rede; mídias de backup; salas técnicas. Controles físicos: controle de acesso às instalações; câmeras; catracas; biometria; fechaduras; vigilância; alarmes; proteção contra incêndio; climatização; nobreak; geradores.

Segurança lógica

Protege recursos por meio de mecanismos tecnológicos e administrativos: senhas; MFA; criptografia; firewall; antivírus; controle de acesso; IAM.

Pegadinha: biometria pode aparecer nos dois contextos — biometria para entrar em uma sala (controle físico); biometria para autenticar em um sistema (controle lógico).

Firewall

Mecanismo que controla o tráfego de rede de acordo com regras estabelecidas. Pode analisar: endereço IP; porta; protocolo; origem; destino; aplicação; estado da conexão. Exemplo: permitir Internet → servidor web → porta 443 e bloquear Internet → banco de dados → porta 1433.

Firewall não é antivírus

Firewall: controla tráfego/comunicações. Antivírus: busca códigos maliciosos. Um firewall não substitui um antivírus.

Proxy

Atua como intermediário entre cliente e servidor. Pode ser utilizado para: controle de acesso; filtragem; registro de navegação; aplicação de políticas; cache; intermediação das comunicações.

IDS e IPS

IDS — Intrusion Detection System: identifica comportamentos ou tráfego suspeito e gera alertas. IDS = detecta e alerta.

IPS — Intrusion Prevention System: além de detectar, pode bloquear ou impedir determinadas atividades. IPS = detecta + atua/previne.

DLP

DLP — Data Loss Prevention — busca identificar e impedir que informações sensíveis sejam: copiadas; enviadas; compartilhadas; transferidas; extraídas indevidamente. Exemplo: um funcionário tenta enviar uma planilha contendo dados sensíveis para um endereço de e-mail externo. Uma solução DLP pode detectar; registrar; alertar; bloquear a transmissão.

CASB

CASB — Cloud Access Security Broker — é uma camada de controle e segurança entre usuários/organizações e serviços de nuvem. Pode auxiliar em: visibilidade; controle de acesso; proteção de dados; aplicação de políticas; conformidade; identificação de uso inadequado de serviços cloud.

SIEM

SIEM — Security Information and Event Management — é uma plataforma destinada à coleta, centralização, correlação e análise de eventos de segurança. Pode receber informações de firewalls; servidores; sistemas; aplicações; endpoints; dispositivos de rede; serviços cloud.

Exemplo: várias tentativas de autenticação falhadas + login bem-sucedido + acesso incomum a dados → alerta de segurança.

Antivírus

Detecta, bloqueia e/ou remove software malicioso. Pode utilizar: assinaturas; análise comportamental; heurística; reputação; análise baseada em padrões.

EDR

EDR — Endpoint Detection and Response — é voltado para detecção e resposta em endpoints (computador; notebook; servidor; estação de trabalho). Fornece maior visibilidade sobre comportamentos ocorridos nos endpoints.

WAF — Web Application Firewall — é um firewall especializado na proteção de aplicações web. Pode ajudar a detectar/bloquear ataques direcionados a aplicações HTTP/HTTPS: SQL Injection; XSS; padrões maliciosos em requisições; comportamentos anômalos.

Pegadinha: firewall tradicional — foco em tráfego de rede. WAF — foco na proteção de aplicações web.

Gestão de vulnerabilidades

Uma vulnerabilidade é uma fraqueza que pode ser explorada para comprometer um ativo. A gestão envolve: identificação; avaliação; priorização; tratamento; correção; validação; acompanhamento.

Monitoração de segurança

Acompanhar continuamente sistemas; redes; servidores; aplicações; endpoints; acessos; eventos. Objetivo: identificar falhas; anomalias; indisponibilidade; ataques; comportamento suspeito.

Backup

Cópia dos dados destinada à recuperação em caso de perda; corrupção; falha; desastre; exclusão acidental; ransomware. É necessário pensar em frequência; retenção; localização; proteção; restauração; testes de recuperação. Pegadinha: backup que nunca foi testado pode não ser confiável.

Regra 3-2-1 de backup

Manter 3 cópias dos dados, em 2 tipos de mídia, sendo 1 cópia fora do ambiente principal.

Malware

Malicious software — software desenvolvido para realizar ações maliciosas. Exemplos: vírus; worm; ransomware; spyware; rootkit; trojan; bot.

Vírus

Normalmente depende de um arquivo/programa hospedeiro para se propagar. Pode modificar arquivos; danificar informações; executar código malicioso.

Worm

Capaz de se propagar de forma mais autônoma entre sistemas. Vírus: geralmente depende de hospedeiro/execução. Worm: possui capacidade de autorreplicação e propagação autônoma.

Ransomware

Malware utilizado para extorsão, frequentemente envolvendo criptografia ou bloqueio de dados/sistemas. O atacante exige algum tipo de pagamento para supostamente restaurar o acesso ou não divulgar informações.

Spyware

Projetado para espionar/coletar informações. Pode monitorar atividades do usuário ou coletar dados sem autorização.

Rootkit

Conjunto de técnicas/software destinado a manter acesso privilegiado e/ou ocultar sua presença em um sistema. Conceito-chave: persistência + ocultação/privilégios.

Trojan

Programa que aparenta ser legítimo, mas executa ações maliciosas. Exemplo: usuário baixa um suposto aplicativo legítimo, mas o programa contém comportamento malicioso.

Ataques cibernéticos

DDoS

DDoS — Distributed Denial of Service — ataque distribuído cujo objetivo geralmente é provocar indisponibilidade de um serviço. O atacante utiliza múltiplas origens/dispositivos para gerar grande quantidade de tráfego ou requisições.

SQL Injection

Ocorre quando entradas controladas pelo usuário são manipuladas de forma insegura e acabam alterando a lógica de uma consulta SQL. Consequências possíveis: acesso indevido a dados; alteração de informações; exclusão de dados; bypass de determinadas verificações.

Prevenção: consultas parametrizadas; prepared statements; validação de entrada; menor privilégio; tratamento adequado de erros.

XSS

Cross-Site Scripting — ocorre quando conteúdo controlado por um atacante é interpretado pelo navegador da vítima como código executável, normalmente JavaScript.

Tipos de XSS

Stored XSS: conteúdo malicioso armazenado no sistema. Reflected XSS: conteúdo malicioso refletido pela aplicação na resposta. DOM-based XSS: vulnerabilidade relacionada à manipulação insegura do DOM no lado cliente.

Pegadinha: XSS está fortemente relacionado a navegador + aplicação web + execução de script.

CSRF

Cross-Site Request Forgery — ataque no qual o atacante induz um usuário autenticado a realizar uma ação que ele não pretendia realizar. Proteções: tokens anti-CSRF; cookies com configuração adequada; validação de origem quando aplicável; mecanismos de proteção do framework.

Path Traversal

Ocorre quando uma aplicação permite manipular caminhos de arquivos de forma insegura. O atacante tenta escapar do diretório permitido e acessar arquivos fora do escopo esperado. Prevenção: validação rigorosa; normalização de caminhos; uso de identificadores em vez de caminhos fornecidos diretamente pelo usuário; controle de permissões; princípio do menor privilégio.

SAST

Static Application Security Testing — analisa o código-fonte ou artefatos do software sem executar a aplicação. Pode ser integrado ao desenvolvimento e CI/CD.

DAST

Dynamic Application Security Testing — analisa a aplicação em execução. O teste ocorre contra a aplicação funcionando.

IAST

Interactive Application Security Testing — combina características de análise estática e dinâmica, utilizando instrumentação/telemetria dentro da aplicação durante sua execução.

VPN

VPN — Virtual Private Network — cria um canal lógico protegido sobre uma rede que pode não ser confiável. Frequentemente utilizada para: acesso remoto; conexão entre redes; proteção do tráfego.

VPN não é sinônimo de anonimato

Uma VPN pode proteger o tráfego entre determinados pontos, mas não significa automaticamente anonimato completo.

MDM

Mobile Device Management — utilizado para administrar dispositivos móveis corporativos. Pode permitir: aplicação de políticas; configuração; inventário; controle de aplicativos; gerenciamento remoto; bloqueio; apagamento remoto.

SSO

Single Sign-On — permite que o usuário autentique-se uma vez e utilize múltiplos sistemas integrados sem precisar realizar uma nova autenticação independente em cada sistema.

MFA

Multi-Factor Authentication — utiliza dois ou mais fatores de categorias diferentes. Categorias clássicas: algo que você sabe (senha, PIN); algo que você possui (celular, token, chave de segurança); algo que você é (impressão digital, reconhecimento facial).

MFA não é "duas senhas"

Senha + PIN pode representar dois conhecimentos — não caracteriza necessariamente MFA. Já senha + aplicativo autenticador envolve conhecimento + posse.

IAM

Identity and Access Management — conjunto de processos, políticas e tecnologias utilizados para administrar: identidades; autenticação; autorização; acessos; privilégios; auditoria.

Autenticação

Responde: Quem é você?

Autorização

Responde: O que você pode fazer? Exemplo: João é autenticado, mas pode consultar clientes e não excluir clientes; pode acessar determinado sistema e não acessar dados financeiros.

Auditoria

Responde: O que aconteceu? Quem fez? Quando? Exemplo: usuário João acessou determinado relatório às 14h32.

Autenticação × autorização × auditoria

AUTENTICAÇÃO: Quem é você? AUTORIZAÇÃO: O que você pode fazer? AUDITORIA: O que você fez?

RBAC

Role-Based Access Control — o acesso é definido de acordo com papéis/roles. Usuário → Cargo/Papel → Permissões.

ABAC

Attribute-Based Access Control — as decisões de acesso são baseadas em atributos: usuário; cargo; recurso; localização; horário; dispositivo; nível de risco; contexto.

Princípio do menor privilégio

Cada usuário ou sistema deve possuir somente os privilégios necessários para executar sua função. Se ocorrer comprometimento, o menor privilégio reduz o impacto potencial.

NIST SP 800-61 — resposta a incidentes

O NIST SP 800-61 trata do gerenciamento de incidentes de segurança. Uma estrutura tradicionalmente apresentada inclui: preparação; detecção e análise; contenção, erradicação e recuperação; atividade pós-incidente.

Preparação

Antes do incidente: definir políticas; estabelecer responsabilidades; preparar ferramentas; treinar equipes; definir procedimentos; estabelecer canais de comunicação. A ideia é: não improvisar durante uma crise.

Detecção e análise

Identificar o evento; verificar se é incidente; coletar informações; avaliar impacto; determinar escopo; priorizar resposta.

Contenção

Busca impedir que o incidente continue se espalhando. Exemplo: isolar um endpoint comprometido da rede.

Erradicação

Busca eliminar a causa ou presença do incidente. Pode envolver: remoção de malware; correção de vulnerabilidade; eliminação de persistência; alteração de credenciais comprometidas.

Recuperação

Busca restaurar os serviços para operação normal. Pode envolver: restauração de backup; reconstrução de sistemas; validação; monitoramento reforçado.

Pós-incidente

Depois do incidente: documentar; avaliar o que aconteceu; identificar falhas; registrar lições aprendidas; melhorar controles.

Threat Intelligence

Threat Intelligence é inteligência sobre ameaças. Busca transformar dados sobre ameaças em conhecimento útil para tomada de decisão. Pode envolver: ameaças conhecidas; indicadores; grupos; técnicas; tendências; vulnerabilidades; campanhas. O objetivo não é simplesmente coletar informações; é produzir inteligência acionável.

Threat Hunting

Busca proativa por sinais de comprometimento ou atividade maliciosa dentro do ambiente. Em vez de esperar somente por um alerta, a equipe procura ativamente comportamentos suspeitos. Diferença: Threat Intelligence — conhecimento sobre ameaças; Threat Hunting — busca proativa dentro do ambiente.

Pentest

Penetration Test — teste de segurança realizado de forma autorizada para avaliar se vulnerabilidades podem ser exploradas. Objetivos: identificar vulnerabilidades; validar controles; avaliar exposição; produzir evidências; recomendar correções. Atenção: pentest exige autorização e escopo definido.

Pentest × Vulnerability Scanning

Vulnerability scanning: procura vulnerabilidades de forma automatizada. Pentest: busca avaliar, dentro de um escopo autorizado, a possibilidade de exploração e o impacto. Portanto: scanner ≠ pentest.

Black Box, White Box e Gray Box

Black Box: o testador possui pouca informação prévia. Simula mais fortemente uma perspectiva externa. White Box: o testador possui amplo conhecimento do ambiente. Gray Box: possui conhecimento parcial.

Modelagem de ameaças

Threat Modeling é um processo sistemático para identificar: ativos; ameaças; vulnerabilidades; riscos; controles. A ideia é: pensar na segurança antes que o ataque aconteça.

STRIDE

Modelo clássico de categorização de ameaças.

  • S — Spoofing: falsificação de identidade. Exemplo: atacante se passando por outro usuário.
  • T — Tampering: adulteração/modificação indevida. Relaciona-se à integridade.
  • R — Repudiation: repúdio. Entidade pode negar ter realizado determinada ação, especialmente quando faltam registros/evidências adequados.
  • I — Information Disclosure: divulgação indevida de informações. Relaciona-se à confidencialidade.
  • D — Denial of Service: negação de serviço. Relaciona-se à disponibilidade.
  • E — Elevation of Privilege: elevação de privilégio. Exemplo: usuário comum obtém privilégios administrativos.

STRIDE — memorização

S → Spoofing → identidade. T → Tampering → integridade. R → Repudiation → não-repúdio/auditoria. I → Information Disclosure → confidencialidade. D → Denial of Service → disponibilidade. E → Elevation of Privilege → privilégio.

MITRE ATT&CK

Base/conhecimento estruturado de comportamentos adversários observados no mundo real. Organiza: táticas; técnicas; subtécnicas; procedimentos.

Táticas do MITRE ATT&CK

As táticas representam o objetivo do adversário. O framework ajuda a organizar o comportamento do adversário.

Pegadinha: tática ≠ técnica. Tática representa o objetivo; técnica representa como esse objetivo pode ser alcançado.

Gestão de riscos — ISO 31000

A ISO 31000 fornece princípios e diretrizes para gestão de riscos. Conceito básico: risco está relacionado ao efeito da incerteza sobre objetivos.

Na segurança: Ativo → Ameaça → Vulnerabilidade → Risco → Controle → Risco residual.

Ameaça × vulnerabilidade × risco

Ameaça: potencial causador de dano. Vulnerabilidade: fraqueza que pode ser explorada. Risco: efeito potencial resultante da combinação entre ameaça, vulnerabilidade, contexto e impacto.

ISO 22301

Trata de Sistemas de Gestão de Continuidade de Negócios — BCMS. Objetivo: ajudar organizações a preparar-se para interrupções e manter/recuperar atividades críticas.

Continuidade × backup

Backup: recuperação de dados. Continuidade de negócios: capacidade da organização de continuar ou recuperar atividades críticas diante de interrupções. Backup pode ser um componente da estratégia de continuidade.

Sarbanes-Oxley — SOX

A Lei Sarbanes-Oxley (SOX) é uma legislação dos Estados Unidos relacionada à governança corporativa, controles internos e confiabilidade das informações financeiras. Para TI, interessa especialmente a importância dos: controles internos; rastreabilidade; controle de acesso; segregação de funções; auditoria; integralidade dos dados; evidências.

Exemplo: uma pessoa não deveria possuir simultaneamente privilégios incompatíveis para criar + aprovar + executar uma operação financeira crítica — segregação de funções.

Política de segurança da informação

Estabelece: princípios; responsabilidades; regras; diretrizes; comportamentos esperados. Exemplos: política de senhas; política de acesso; política de dispositivos; política de classificação; política de backup; política de uso aceitável.

Política × procedimento

Política: define o que deve ser seguido e quais princípios/regras existem. Procedimento: define como determinada atividade deve ser executada.

Classificação da informação

Determina o nível de proteção necessário. Categorias: pública; interna; confidencial; restrita. A nomenclatura varia conforme a organização. Objetivo: definir quem pode acessar; como armazenar; como transmitir; como proteger; como descartar.

ISO/IEC 27002

Fornece orientações e boas práticas para controles de segurança da informação. Pegadinha importante: não confundir com ISO/IEC 27001. A 27001 está associada aos requisitos para um Sistema de Gestão de Segurança da Informação — SGSI/ISMS — e à certificação do sistema. A 27002 fornece orientação detalhada sobre controles.

Criptografia

Utilizada para proteger informações por meio de técnicas matemáticas. Pode fornecer propriedades como: confidencialidade; integridade; autenticidade; não repúdio.

Criptografia simétrica

Utiliza a mesma chave para operações de criptografia e descriptografia. Vantagem: geralmente eficiente para grandes volumes de dados. Desafio: distribuição segura da chave.

Criptografia assimétrica

Utiliza um par de chaves: chave pública; chave privada. Aplicações: troca/estabelecimento de chaves; criptografia; assinatura digital.

Hash

Função que transforma uma entrada em um valor de tamanho determinado. Características desejáveis: dificuldade de encontrar colisões; resistência à inversão; efeito avalanche. Hash não é simplesmente "criptografia reversível".

Certificado digital

Associa uma identidade a uma chave pública e é emitido/validado dentro de uma infraestrutura de confiança. No contexto da ICP-Brasil, existem autoridades certificadoras e uma cadeia de confiança. O certificado pode ajudar a estabelecer: identidade + chave pública.

Assinatura digital

Utiliza mecanismos criptográficos para fornecer garantias relacionadas a: autenticidade; integridade; não repúdio. De forma simplificada: Documento → Hash → Assinatura com chave privada → Assinatura digital. A verificação utiliza a chave pública correspondente.

Assinatura digital × criptografia

Criptografia para confidencialidade: objetivo de esconder o conteúdo. Assinatura digital: objetivo principal de demonstrar autenticidade e integridade. Uma assinatura digital não tem como objetivo principal tornar o documento secreto.

Segurança em nuvem

Cloud Security trata da proteção de: dados; aplicações; identidades; infraestrutura; configurações; workloads; APIs; serviços cloud.

Responsabilidade compartilhada

Provedor → segurança da infraestrutura que oferece. Cliente → segurança/configuração dos recursos sob sua responsabilidade.

IaaS, PaaS e SaaS

IaaS: cliente possui maior responsabilidade sobre sistema operacional; aplicações; configurações; dados. PaaS: provedor gerencia mais componentes da plataforma; cliente continua responsável por aplicação; dados; identidades; configurações pertinentes. SaaS: provedor gerencia grande parte da infraestrutura e aplicação; cliente continua tendo responsabilidades, especialmente relacionadas a usuários; dados; configurações; permissões.

Principais riscos de segurança em cloud

Configuração incorreta; exposição indevida de dados; credenciais comprometidas; permissões excessivas; APIs inseguras; falta de monitoramento; ausência de criptografia adequada.

Exemplo: um armazenamento cloud é configurado acidentalmente como público. O problema não é necessariamente uma falha do provedor; pode ser erro de configuração do cliente.

Segurança em IoT

IoT — Internet of Things — representa dispositivos conectados capazes de coletar, processar ou transmitir dados. Exemplos: sensores; câmeras; dispositivos industriais; equipamentos inteligentes.

Riscos em IoT

Hardware limitado; software desatualizado; credenciais padrão; interfaces inseguras; comunicação inadequadamente protegida; falta de gerenciamento centralizado; grande quantidade de dispositivos.

Segurança de IoT

Boas práticas: alterar credenciais padrão; atualizar firmware; segmentar redes; controlar acesso; criptografar comunicações quando aplicável; monitorar dispositivos; manter inventário; remover dispositivos obsoletos.

Acesso indevido — conceito fundamental

Maria trabalha no setor administrativo. Ela consegue autenticar-se no sistema. Entretanto, devido a uma configuração incorreta, Maria consegue consultar informações financeiras restritas às quais não deveria ter acesso. Maria foi autenticada corretamente, porém não estava autorizada a acessar aquele recurso. Temos um problema de autorização/controle de acesso. Portanto: autenticação ≠ autorização.

Defesa em camadas

Uma arquitetura segura não depende de um único mecanismo. Pode utilizar: Usuário → MFA → IAM → Firewall → WAF → Aplicação → Banco → DLP → SIEM → Backup. Se uma camada falhar, outras podem reduzir o impacto. Conceito: defesa em profundidade.

Segurança preventiva, detectiva e corretiva

Preventiva: busca impedir o incidente. Exemplos: firewall; MFA; controle de acesso; hardening. Detectiva: busca identificar o problema. Exemplos: IDS; SIEM; monitoração; EDR. Corretiva: busca restaurar/corrigir. Exemplos: recuperação de backup; remoção de malware; correção de vulnerabilidade.

Fluxo completo de segurança

IDENTIFICAR → PROTEGER → DETECTAR → RESPONDER → RECUPERAR → APRENDER

Questões modelo

Questão 1: Qual componente da tríade CIA está diretamente relacionado à proteção contra acesso não autorizado? Resposta: B — Confidencialidade.

Questão 2: Qual tecnologia é especializada na proteção de aplicações web? Resposta: B — WAF.

Questão 3: Qual mecanismo é principalmente utilizado para centralizar e correlacionar eventos de segurança? Resposta: A — SIEM.

Questão 4: Qual é a principal diferença entre IDS e IPS? Resposta: B — IDS detecta e IPS pode detectar e prevenir/bloquear.

Questão 5: Qual ataque tem como característica principal provocar indisponibilidade por meio de múltiplas origens? Resposta: C — DDoS.

Questão 6: Qual técnica analisa o código sem executar a aplicação? Resposta: B — SAST.

Questão 7: Qual modelo de controle de acesso utiliza papéis? Resposta: B — RBAC.

Questão 9: No STRIDE, "Elevation of Privilege" significa: Resposta: D — elevação de privilégio.

Questão 10: No contexto do MITRE ATT&CK, uma tática representa principalmente: Resposta: B — o objetivo do adversário.

Pegadinhas de prova — as mais importantes

  1. IDS × IPS: IDS detecta. IPS pode detectar e prevenir.
  2. Firewall × WAF: firewall → controle de tráfego. WAF → aplicação web.
  3. Antivírus × EDR: antivírus → malware/proteção. EDR → visibilidade, detecção e resposta no endpoint.
  4. SIEM: não é apenas armazenamento de logs. Diferencial: centralização + correlação + análise + geração de alertas.
  5. RBAC × ABAC: RBAC = papel. ABAC = atributos/contexto.
  6. Autenticação × autorização: autenticação = quem é? autorização = pode fazer o quê?
  7. SAST × DAST: SAST = estático. DAST = dinâmico.
  8. XSS × SQL Injection: XSS → aplicação/navegador/script. SQL Injection → consulta/banco de dados.
  9. Backup × continuidade: backup = recuperação de dados; continuidade = capacidade de manter/recuperar atividades críticas.
  10. Criptografia × assinatura digital: criptografia → principalmente confidencialidade; assinatura → autenticidade + integridade + evidência de autoria/não repúdio.
  11. ISO 27001 × ISO 27002: 27001 → requisitos do SGSI. 27002 → orientação sobre controles.
  12. STRIDE × MITRE ATT&CK: STRIDE → modelagem/categorização de ameaças. MITRE ATT&CK → conhecimento de comportamentos adversários, táticas e técnicas.

User Experience — UX

Material de Estudo — Transpetro · Ênfase 5 — UX, Usabilidade, Acessibilidade e Design

A ideia central é: UX não é apenas deixar uma tela bonita. É projetar produtos e serviços considerando as necessidades, limitações, objetivos e contexto das pessoas que irão utilizá-los.

Acessibilidade e Usabilidade

O que é acessibilidade?

Acessibilidade é a característica que permite que pessoas, incluindo pessoas com deficiência, possam perceber, compreender, navegar e interagir com um produto, serviço ou conteúdo. No contexto de software e aplicações web, significa projetar a interface para que ela possa ser utilizada pelo maior número possível de pessoas.

Exemplos: navegação por teclado; textos alternativos para imagens; contraste adequado; legendas em vídeos; compatibilidade com leitores de tela; identificação clara de campos de formulário; mensagens de erro compreensíveis; foco visual adequado; possibilidade de redimensionamento do texto.

Exemplo prático de acessibilidade

Imagine uma tela de cadastro de carga visualmente bonita. Ela pode ainda ser inacessível se: o botão só puder ser acionado com mouse; os campos não tiverem rótulos adequados; o contraste for insuficiente; o leitor de tela não conseguir identificar os elementos. Então usuários com determinadas limitações podem ter dificuldades para utilizar o sistema.

Acessibilidade não significa apenas deficiência

Embora esteja fortemente relacionada à inclusão de pessoas com deficiência, seus benefícios podem alcançar qualquer usuário. Exemplo: uma legenda em um vídeo pode ser essencial para uma pessoa surda, mas também útil para alguém em ambiente onde não pode usar áudio. Uma interface navegável por teclado é importante para determinadas pessoas com deficiência, mas também pode aumentar a produtividade de usuários avançados.

Acessibilidade permanente × situacional

Uma pessoa pode ter uma limitação: permanente; temporária; situacional.

  • Permanente: pessoa com deficiência visual.
  • Temporária: pessoa com o braço imobilizado.
  • Situacional: pessoa segurando uma criança.

Uma boa UX considera diferentes contextos de utilização.

WCAG

A WCAG — Web Content Accessibility Guidelines — é uma referência internacional para acessibilidade de conteúdo web. Um conceito extremamente importante é o conjunto dos quatro princípios POUR:

  • P — Perceptível: a informação deve poder ser percebida.
  • O — Operável: o usuário deve conseguir operar a interface.
  • U — Compreensível: a informação e a operação devem ser compreensíveis.
  • R — Robusto: o conteúdo deve funcionar adequadamente com diferentes tecnologias assistivas e agentes de usuário.

Para memorizar: POUR = Perceptível, Operável, Compreensível e Robusto.

Usabilidade

Usabilidade está relacionada à facilidade com que usuários conseguem utilizar um sistema para atingir seus objetivos com eficácia; eficiência; satisfação.

Uma interface pode ser muito fácil para determinado usuário, mas inacessível para outro.

Feedback

O sistema deve informar ao usuário o resultado de suas ações. Ruim: usuário clica em Salvar e nada acontece visualmente. Melhor: "Salvando..." → "Carga cadastrada com sucesso."

Prevenção de erros

Uma boa interface tenta evitar erros antes que ocorram. Se o campo aceita apenas números, em vez de simplesmente gerar erro posteriormente, a interface pode impedir ou orientar a entrada incorreta.

Mensagens de erro

Mensagem ruim: "Erro 500." Mensagem melhor: "Não foi possível concluir o cadastro porque o serviço de cargas está indisponível. Tente novamente." Uma boa mensagem informa o problema, evita linguagem excessivamente técnica e orienta o usuário sobre o que fazer.

Affordance

Característica de um elemento que sugere como ele pode ser utilizado. Exemplo: [ ENVIAR ] — o formato sugere que é um botão. Um elemento que parece botão, mas não responde ao clique, gera confusão.

Consistência

Elementos semelhantes devem funcionar de maneira semelhante. Se "Salvar" é representado por determinado padrão em uma tela, não é recomendável que outra tela use comportamento completamente diferente sem motivo.

Reconhecimento versus memorização

Uma boa interface favorece reconhecer opções em vez de obrigar o usuário a memorizar comandos. Ruim: Digite: CMD-034-X. Melhor: Tipo de operação: [Cadastro ▼].

Histórias do usuário

O que é uma história do usuário?

Uma User Story descreve uma necessidade do usuário sob sua perspectiva. Formato clássico: Como [papel], quero [objetivo], para [benefício].

Exemplo: Como operador logístico, quero consultar a localização de uma carga, para acompanhar seu transporte.

História do usuário não é requisito técnico detalhado

Evite: "Como usuário, quero utilizar Angular 19 para implementar uma tela." Isso descreve tecnologia, não valor de negócio. Melhor: "Como operador, quero consultar cargas em trânsito para acompanhar as operações."

Critérios de aceitação

Definem condições que precisam ser atendidas para considerar a história concluída.

BDD e Gherkin

Formato importante para integração entre requisitos e testes. Estrutura: Dado / Quando / Então.

Exemplo:

Cenário: Consultar carga existente
Dado que o operador esteja autenticado
Quando informar o código "CARGA123"
Então o sistema deve apresentar os dados da carga

INVEST

Uma boa User Story costuma ser avaliada pelo acrônimo INVEST: Independent (independente); Negotiable (negociável); Valuable (valiosa); Estimable (estimável); Small (pequena); Testable (testável).

Pegadinha: User Story não precisa ser uma especificação técnica gigantesca. Ela deve permitir conversação e refinamento.

Desenho e planejamento da interação

O que é interação?

É a forma como o usuário interage com o software: Usuário → Interface → Sistema → Resposta → Usuário.

Fluxo de usuário

Representa o caminho que o usuário percorre para realizar uma tarefa. Exemplo: Login → Dashboard → Consultar carga → Informar código → Pesquisar → Visualizar resultado.

Arquitetura de informação

Organização das informações para facilitar sua localização e compreensão. Uma arquitetura ruim pode fazer o usuário se perder mesmo que as funcionalidades estejam corretas.

Wireframe

Representação estrutural da interface. Normalmente enfatiza: disposição; hierarquia; componentes; navegação.

Mockup

Representação visual mais detalhada da interface. Pode apresentar: cores; tipografia; imagens; componentes; espaçamento.

Protótipo

Pode possuir diferentes níveis de fidelidade. Baixa fidelidade: [ botão ] [ campo ] [ menu ]. Alta fidelidade: a interface se aproxima visualmente do produto final.

User-Centered Design — UCD

O Projeto Centrado no Usuário coloca o usuário no centro do processo de desenvolvimento. A equipe procura compreender: quem utiliza; quais são seus objetivos; quais dificuldades possui; em qual contexto trabalha; quais são suas necessidades.

Ciclo centrado no usuário

Pesquisar usuários → Compreender necessidades → Projetar → Prototipar → Testar com usuários → Obter feedback → Melhorar. É um processo iterativo.

Exemplo real

Imagine um sistema utilizado por operadores durante uma atividade crítica. A equipe acredita que "o dashboard deve mostrar 30 indicadores". Durante testes com operadores, descobre-se que "só precisamos de cinco indicadores durante a operação; os demais atrapalham". O projeto centrado no usuário permite descobrir isso antes de finalizar o produto.

Contexto de uso

UX não deve considerar apenas "o usuário está sentado em frente ao computador". É necessário considerar: ambiente; dispositivo; pressão de tempo; iluminação; ruído; conectividade; experiência do usuário; riscos da atividade.

Storytelling com dados

O que é storytelling com dados?

Utilização de dados para construir uma narrativa que permita ao público compreender rapidamente o que os dados significam e qual conclusão pode ser extraída. Não é simplesmente colocar gráficos em uma tela.

Dado sem narrativa

Janeiro 1.200; Fevereiro 1.250; Março 1.400; Abril 1.850; Maio 2.100. O usuário vê números.

Dado com narrativa

"Volume de cargas aumentou 75% em cinco meses, exigindo avaliação da capacidade operacional." Agora temos: Dado → Análise → Contexto → Insight → Ação.

Elementos do storytelling

Contexto (por que estamos olhando os dados?); Conflito/problema (o que está acontecendo?); Evidência (o que os dados mostram?); Insight (o que podemos concluir?); Ação (o que devemos fazer?).

Relatórios e dashboards

Relatório

Normalmente possui informações mais detalhadas e estruturadas. Exemplo: relatório mensal de cargas (Carga, Origem, Destino, Peso, Status).

Dashboard

Interface visual destinada a acompanhar indicadores e apoiar análise e decisão.

KPI

Key Performance Indicator é um indicador-chave de desempenho. Exemplo: percentual de entregas no prazo. Um KPI deve estar relacionado a um objetivo relevante.

Dashboard operacional

Foco: O que está acontecendo agora? Exemplos: cargas em trânsito; alertas; operações pendentes; incidentes.

Dashboard gerencial

Foco: Como está o desempenho? Exemplos: produtividade; custos; atrasos; metas.

Dashboard estratégico

Foco: Estamos atingindo os objetivos estratégicos? Exemplos: crescimento; eficiência; indicadores estratégicos; metas corporativas.

Escolha de gráficos

Comparação: gráfico de barras. Evolução temporal: gráfico de linhas. Composição: barras empilhadas ou outras representações apropriadas. Relação entre variáveis: dispersão.

Evite gráficos enganosos

Se o eixo vertical for manipulado para começar em 90, pequenas diferenças podem parecer enormes. A escala precisa ser apresentada de maneira que não induza interpretação equivocada.

Princípio da simplicidade

Um dashboard não deve mostrar tudo simplesmente porque é possível. Pergunte: "Qual decisão esse indicador ajuda o usuário a tomar?" Se não ajuda em nenhuma decisão relevante, talvez não precise estar no dashboard principal.

Interoperabilidade

É a capacidade de um sistema ou interface funcionar adequadamente em diferentes ambientes. No contexto web: Aplicação → Chrome, Firefox, Edge, Safari, outros.

Por que existe problema entre navegadores?

Os navegadores podem apresentar diferenças em: implementação de padrões; APIs; CSS; JavaScript; recursos experimentais; mecanismos de renderização.

Exemplo

Uma funcionalidade funciona no Chrome, mas apresenta comportamento inesperado no Safari. Isso pode indicar problema de compatibilidade ou uso inadequado de recursos.

Boas práticas

Utilizar: padrões web; HTML semântico; CSS compatível; APIs padronizadas; testes em diferentes navegadores; ferramentas de compatibilidade.

Progressive Enhancement

A ideia é: construir uma experiência básica funcional e acrescentar recursos avançados quando houver suporte. HTML básico → CSS → JavaScript → Recursos avançados. Se determinado recurso não estiver disponível, a funcionalidade básica continua utilizável.

Graceful Degradation

É projetar uma solução completa para ambientes modernos e garantir que ela degrade de maneira aceitável em ambientes com menor capacidade.

Diferença simplificada: Progressive Enhancement — começa pelo básico e adiciona recursos. Graceful Degradation — começa completo e garante uma experiência aceitável quando recursos não funcionarem.

MVP

O que é MVP?

MVP — Minimum Viable Product — Mínimo Produto Viável. É uma versão mínima de um produto capaz de entregar valor suficiente para permitir aprendizado e validação de hipóteses com usuários.

MVP não significa software malfeito

MVP não significa "fazer qualquer coisa rapidamente". Significa entregar o mínimo necessário para testar uma hipótese relevante e aprender com o uso real.

Exemplo

Produto completo: Rastreamento + Chat + Notificações + Mapas avançados + Relatórios + Gamificação + Integrações. MVP: Login + Consulta de carga + Localização. Se a hipótese for "Usuários precisam acompanhar cargas pelo celular", o MVP permite validar essa hipótese.

MVP × protótipo

Não são necessariamente a mesma coisa. Protótipo: pode ser usado para explorar uma ideia ou interação; pode não ter funcionamento real. MVP: é um produto mínimo funcional, criado para obter aprendizado real com usuários/mercado.

Prototipação

O que é prototipação?

Criar uma representação de uma solução antes de construir a versão definitiva. Objetivos: validar ideias; testar fluxos; descobrir problemas; obter feedback; reduzir riscos.

Fidelidade

Baixa fidelidade: rápida e simples. Alta fidelidade: pode simular aparência; navegação; animações; interações.

Protótipo descartável

É criado para aprender. Depois pode ser descartado.

Protótipo evolucionário

É gradualmente refinado até contribuir para a solução final.

Design Thinking

O que é Design Thinking?

Abordagem para resolução de problemas complexos com forte foco em: pessoas; necessidades; experimentação; colaboração; criatividade; aprendizado.

Etapas clássicas

Empatizar → Definir → Idear → Prototipar → Testar. Atenção: essas etapas não devem ser interpretadas como uma sequência rígida e obrigatória. O processo pode ser iterativo.

Empatia

Busca compreender o usuário. Perguntas: o que ele precisa? quais são suas dificuldades? como trabalha? o que sente? quais são suas limitações?

Definição

Transformar observações em um problema claramente definido. Em vez de "Precisamos melhorar o sistema", definir: "Operadores têm dificuldade para identificar rapidamente cargas atrasadas durante períodos de alta demanda."

Ideação

Gerar possíveis soluções. Problema → Brainstorming → Solução A, B, C, D.

Prototipação

Transformar ideias em representações que possam ser experimentadas.

Teste

Usuários interagem com a solução e fornecem feedback. Protótipo → Usuário → Feedback → Alteração → Novo protótipo.

Pensamento divergente e convergente

Divergente: expandir possibilidades (1 ideia → 10 ideias → 30 ideias). Convergente: selecionar e refinar alternativas (30 ideias → 10 → 3 → 1 solução).

Personas

O que é uma persona?

Persona é uma representação semifictícia, baseada em dados e pesquisas, de um tipo relevante de usuário. Não é simplesmente "inventar um usuário". Ela deve ser baseada em evidências.

Exemplo de persona

PERSONA: Carlos. Cargo: Operador logístico. Experiência: 8 anos. Objetivo: Acompanhar cargas rapidamente. Dificuldades: sistemas lentos; muitos campos; informações espalhadas. Necessidades: busca rápida; alertas; dashboard simples.

Persona × usuário real

A persona não representa necessariamente uma pessoa específica. Ela representa um perfil de usuário. 50 operadores → 1 pesquisa → 1 padrão de comportamento → 1 PERSONA.

Persona primária

Representa o principal grupo de usuários para o qual o produto é projetado.

Personas secundárias

Representam outros grupos importantes. Exemplo: Persona primária: Operador. Persona secundária: Gestor, Auditor.

Papel × persona

Papel: representa a função exercida. Exemplo: Operador. Persona: representa um perfil de usuário com características, objetivos, comportamentos e necessidades. Uma persona pode exercer determinado papel.

Mapa de empatia

Pode ajudar a compreender uma persona. Pergunta: O que pensa? O que sente? O que vê? O que ouve? O que fala? O que faz? Quais suas dores? Quais seus ganhos?

Exemplo integrado

Imagine um sistema de acompanhamento de cargas. Persona: Carlos, operador logístico. Problema: ele precisa consultar dezenas de cargas rapidamente. User Story: como operador, quero pesquisar uma carga pelo código para localizar rapidamente sua situação. Protótipo: consultar carga (código + pesquisar). Critério de aceitação: dado que o operador esteja autenticado, quando informar um código válido, então os dados da carga devem ser apresentados. Dashboard: cargas em trânsito 1.245; atrasadas 87; entregues hoje 324. Teste: o operador utiliza o protótipo. Feedback: "Preciso conseguir pesquisar também por placa."

Acessibilidade dentro desse processo

A acessibilidade deve ser considerada desde o início, e não somente no final. Um processo ruim seria: Desenvolver → Publicar → Descobrir que é inacessível → Corrigir. Um processo melhor: Pesquisa → Requisitos → Design acessível → Protótipo acessível → Teste com usuários → Desenvolvimento → Testes.

UX e acessibilidade na prática

Imagine um botão vermelho. Um usuário pode entender que vermelho significa alguma coisa. Mas depender somente da cor pode gerar problemas. Uma alternativa: botão com texto "Cancelar". A informação passa a ser transmitida também por texto. Conceito importante: não dependa exclusivamente de cor para transmitir informação.

Usabilidade heurística

Um conceito clássico de UX é a avaliação heurística. Entre heurísticas conhecidas de Nielsen estão:

  1. Visibilidade do estado do sistema;
  2. Correspondência entre sistema e mundo real;
  3. Controle e liberdade do usuário;
  4. Consistência e padrões;
  5. Prevenção de erros;
  6. Reconhecimento em vez de memorização;
  7. Flexibilidade e eficiência;
  8. Design minimalista;
  9. Ajuda para reconhecer, diagnosticar e recuperar erros;
  10. Ajuda e documentação.

Exemplo: após clicar em "Salvar", mostrar "Salvando..." atende à ideia de visibilidade do estado do sistema.

Uma questão pode juntar praticamente todo o conteúdo

Uma equipe precisa desenvolver um sistema para operadores logísticos. Antes do desenvolvimento, pesquisa os usuários, cria personas, identifica suas dificuldades, elabora protótipos, testa a interface com os usuários e desenvolve uma versão mínima para validar a solução. O dashboard apresenta apenas os indicadores necessários às decisões dos gestores e a interface deve ser acessível e funcionar em diferentes navegadores.

Nesse cenário, aparecem simultaneamente: Personas + Design Thinking + UCD + Prototipação + MVP + Dashboard + UX + Acessibilidade + Interoperabilidade.
